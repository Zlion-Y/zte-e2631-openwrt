## 一、任务与结论摘要

目标两条硬需求：
1. 产物能经原厂 Web 升级页 `supgrade.html` 直刷；
2. 能从 OpenWrt 内部改 A/B 槽启动选择标记退回原厂。

**结论：两条都有同平台先例可循，机制已逐字节验死，不存在"能不能"的问题，剩下的全是工程量。**

- 需求②的规格完全清楚（§三），可直接写成一个 ~400 行的 C 程序。
- 需求①的包格式完全清楚（§二），可用一个模板重封脚本实现；`supgrade.html` 与 `fw_flashing` 是同一个刷写器，包合法即可刷。
- 真正的工程量在**移植本身**：你的 mainline 树目前「能 TFTP 跑到 shell」，但 **SPI-NAND、有线网络、SMP 都还没做**（§四），这三块才是决定能否日常可用的关键路径。

## 二、原厂升级包格式（A 级，6B5/7B5/8B8 三包全部验算通过）

```
0x000  16B 外层魔数 99999999 44444444 55555555 aaaaaaaa
0x010  4B  hdr_ofs = 0（= 未签名包，原厂 VerifySign 跳过）
0x014  512B 版本头 verhdr            ← 下文偏移一律用「相对 verhdr 起点」
0x214  body 开始，被**整段原样**写入目标槽（按坏块跳过）
         body+0x000  32B 槽标记 33333333 cccccccc 88888888 dddddddd + 16×FF
         body+0x020  kernel extent（明文 legacy uImage，load=entry=0x40008000，comp=0）
         ...        0x214 字节的 0x00 填充（6B5/7B5/8B8 实测全零）
         body+0x340000  rootfs extent
```

verhdr 关键字段（相对 verhdr；**文件偏移 = 下列值 + 0x14**）：

| 偏移 | 含义 | 7B5 实测 |
|---|---|---|
| +0x08 / +0x0c | upgradeKey1 / Key2 | 0x1351 / 0x5211 |
| +0x10 | 版本串 32B | `V1.0.0.7B5.8000` |
| +0x30 | **body 总大小**（cnjn 的 `H_FW_SIZE`，`package_load()` 会检查它等于 body 长度）。E2631 四个官方包里它同时**等于** `ROUND_UP(body_len, 0x20000)`，因为原厂把 rootfs 尺寸都取成 128 KiB 的整数倍 —— 两种读法在这四个包上不可区分 | 0x1560000 |
| +0x34/+0x38/+0x3c | kernel size / **包内绝对文件偏移** / CRC32 | 0x33FDCC / 0x234 / 0x9EF7C246 |
| +0x40/+0x44/+0x48 | rootfs size / 文件偏移 / CRC32（**对存放的字节算**） | 0x1220000 / 0x340214 / 0x3DF85EE2 |
| +0x4c..0x58 / +0x5c..0x68 | 槽 A / 槽 B 描述 {base, span, 0, 0x1000000} | 0x700000,0x1C00000 / 0x2300000,0x1C00000 |
| +0x6c | 产品串 52B | `ZXHN E2631 V1.0.0` |
| +0x8c / +0x98 | 含 bootloader 标志（保持 0）/ U-Boot CRC | 0 |
| **+0xa4** | **CRC1 = CRC32(verhdr[0x00:0xa4])** | 三包 + 两片活槽头全部 MATCH |
| +0xa8 | 构建时间串 16B | `20250925221124` |
| +0xb8 | 原厂 switch 要求为 0（"version integrality"） | |
| +0xc4 / +0xc8 | flash 容量 / 块对齐 | 0x08000000 / 0x10000 |
| +0xf4 | 内层魔数 `333333336666666699999999cccccccc` | |
| +0x110 | 硬件版本串 | 7B5=`V1.0.0`，8B8=`V1.1.1` |
| +0x1e0..0x1ec | 槽表 {A起点, B起点, B起点, B终点} | 0x700000,0x2300000,0x2300000,0x3F00000 |
| +0x1f0 | **本头部所在槽基址（包里是 0，刷写时盖章）** | 槽A活头部=0x700000，槽B=0x2300000 |
| +0x1f4 | **serial（包里恒为 1，刷写时写 maxversionum+1）** | 活机两槽都 = 0x10 |
| +0x1f8 | 新版本标志，刷后 = 1 | 1 |
| **+0x1fc** | **CRC2 = CRC32(verhdr[0x00:0x1fc])**（覆盖 serial） | MATCH |

**决定性一条（A 级）**：把官方包的 verhdr 与真机 flash 里的槽头逐字节比对，
512 字节中**只有 +0x1f0 / +0x1f4 / +0x1f8 / +0x1fc 四处不同**（其余含 CRC1 完全一致）。
cnjn 在 SR1010 上独立实测同一结论 → 跨机型互证。

**密文归属（A 级，推翻旧文档）**：
- **kernel extent 是明文 uImage**（三包首 4 字节都是 `27 05 19 56`；真机 `mtdblock0` 在 0x700000+0x20 与 0x2300000+0x20 都读出明文头，size 0x3329A6、load=entry=0x40008000）。
- **rootfs extent 是 AES-128-ECB 密文**（key `E263111559d0dfde`），rootfs 的 CRC **对密文字节算**。
- 解密发生在**原厂内核按分区的软件读路径**，不是控制器硬件、不是 U-Boot：
  同一器件两个视图 —— `/dev/mtdblock8+0 = 85 19 01 e0`(明文 JFFS2)，而
  `/dev/mtdblock0+0xA40000 = 20 7c a1 cc …`(密文)，`/dev/mtdblock0+0x2640000` 与之逐字节相同。
- ⇒ **OpenWrt 侧一律写明文**（kernel 明文本来就得，rootfs 也写明文并**对明文算 CRC**）。
  不需要、也不应该移植任何 AES 解密层。

## 三、A/B 槽与选槽规则（需求②的完整规格）

- 槽 A `0x700000..0x2300000`、槽 B `0x2300000..0x3F00000`，各 28 MiB，**每槽各带一份完整 kernel+rootfs+槽头**（非共享 rootfs）。
- 当前槽由 U-Boot 经 bootargs 传下来：`/proc/cmdline` 尾部 7 段
  `... U-Boot V1.0.0 20250325110003 0x700000 0x0 0xaf 0xa3`，第 4 段 = 当前槽基址（A 级实测）。
- `/proc/zte/verinfo/versionstates`（A 级实测全文）给出 cur/back 的 headeraddr、serial、isbad、
  `maxversionum=0x10`、槽表、`curUpgradeKey1/2`。**注意它是开机快照，写完 flash 不更新**（B 级，cnjn 实测）。
- **U-Boot(cspboot) 选槽算法**（B 级反编译 + 本机间接验证）：
  每 128 KiB 扫整片 flash 找内层魔数，**只校验 CRC1**（不看 CRC2）；
  `slot0.serial < slot1.serial` 或 `slot0.serial == 0` → 起 slot1；否则起 slot0；**相等起 slot0**；
  **选中的槽起不来不会自动换槽**（所以任何自测都必须留好退路）。
  本机间接验证：两槽 serial 都是 0x10 → 仍起槽 A，与我误操作同步槽 B 后的实际现象一致。
- **回原厂的实现**（不需要破坏任何固件本体）：
  1. 读我方槽的 512B 槽头（用 `slot_scan`：按擦除块扫，验内层魔数 + CRC1）；
  2. **先完整校验目标（原厂）槽**：kernel/rootfs 两段 CRC 按坏块跳读重放 —— 因为"不会自动回退"，
     绝不能把启动指向一个坏槽；
  3. 把目标槽槽头的 `+0x1f4 serial` 改成 `max_serial()+1`，重算 `+0x1fc CRC2`（**CRC1 覆盖 [0:0xa4]，不受 serial 影响**）；
  4. **先 MEMERASE 那个 128 KiB 块，再整块写回**（尾部补 0xFF）。
     原厂 `fw_flashing -v switch` 的 bug 就是不擦除就地写 → NAND 按位与 → serial 不变大、CRC2 报废、
     而且它的错误判断反了（`CspUserMtdWrite` 失败返回 1，调用方把 `>=0` 当成功）、写完不回读。**别用原厂那条命令。**
- 现成参考实现：`refs-cnjn/zte-fwslot/src/zte-fwslot.c`（741 行，含 `check/flash/switch/info[-j]`、
  靠 `/sys/class/mtd/mtdN/offset` 反查槽分区、LD_PRELOAD 假 mtd 测试套件）
  + `refs-cnjn/zte/base-files/lib/upgrade/platform.sh`（sysupgrade 挂接）
  + `refs-cnjn/zte/package/utils/luci-app-zte-fwslot`（LuCI 按钮 + rpcd + acl）。
  搬到 E2631 只需改：`slot_start={0x700000,0x2300000}`、`UBOOT_SIZE=0`、`KERNEL_MAGIC_SIZE=32`（**保留**，实测槽首确有 32B 标记）、
  `PRODUCT="ZXHN E2631 V1.0.0"`、去掉 U-Boot 那段 CRC region、运行槽改从 `/proc/cmdline` 取。

# 追加核验（2026-10-13 深夜）：槽版本头的**活体逐字节验证**

`device/pass20.out.txt` 用 `busybox hexdump -v -e '16/1 "%02x"'` 从真机 `/dev/mtdblock0` 取到两个**在用的**
版本头原文，`tools/check_hdr_dump.mjs` 解码并实算 CRC：

| 字段 | 槽 A（0x1C60000） | 槽 B（0x3860000） | 含义 |
|---|---|---|---|
| +0x08/+0x0C | 0x1351 / 0x5211 | 同 | 升级 key 对（= versionstates 的 curUpgradeKey1/2）✓ |
| +0x10 | "V1.0.0.7B5.8000" | 同 | 版本串 |
| +0x30 | 0x01560000 | 0x01560000 | **body 长度**；头就在 body 之后的那一块 ✓ |
| +0x34/+0x38/+0x3C | 0x33fdcc / 0x234 / 0x9ef7c246 | 同 | 内核大小/包内偏移/CRC |
| +0x40/+0x44/+0x48 | 0x01220000 / 0x340214 / 0x3df85ee2 | 同 | rootfs 大小/偏移/CRC（7B5 尺寸，与 mtd8 的 0x1220000 一致 ✓） |
| +0x4C/+0x50 | 0x700000 / 0x1C00000 | 同 | 槽 A 基址/跨度 |
| +0x5C/+0x60 | 0x2300000 / 0x1C00000 | 同 | 槽 B 基址/跨度 |
| +0x1E0..0x1EC | [0x700000, 0x2300000, 0x2300000, 0x3F00000] | 同 | 槽表（与 versionstates 四项逐字对应 ✓） |
| **+0x1F0** | **0x700000** | **0x2300000** | **本槽起点 —— 两槽唯一的实质差异** |
| +0x1F4 | 16 | 16 | serial（与 versionstates 的 cur/back = 0x10 一致 ✓） |
| +0x1F8 | 1 | 1 | isNew |
| +0x8C / +0x98 | 0 / 0 | 0 / 0 | 不含 U-Boot ✓（E2631 包体里没有引导） |
| +0xF4 | 33333333 66666666 99999999 cccccccc | 同 | 内魔数 ✓ |
| **+0xA4 (CRC1)** | 0x6e61dfdb = **实算一致** | 同 | CRC32(hdr[0:0xa4]) ✓ |
| **+0x1FC (CRC2)** | 0x1bfce530 = **实算一致** | 0xabb0ca16 = **实算一致** | CRC32(hdr[0:0x1fc]) ✓ |

三条直接结论：

1. **本工作区的 verhdr 字段表与 CRC 双算在活体镜像上完全成立**（不是从包反推的自洽，而是真机 bootable 头）。
2. **两槽头只差 +0x1F0（和由此变动的 CRC2）** ⇒ `e2631-fwslot flash` 里"抄包头 → 改写 slotStart/serial/isNew → 只重算 CRC2"
   的做法，与原样被刷写器盖章的结果**同构**；CRC1 覆盖 [0:0xa4] 不含这些字段，所以盖章不会破坏 CRC1 ✓。
3. **官方包头的 +0x1F0=0 / serial=1 / isNew=0**（`out/pkg8b8-hdr.txt` 同工具解出），
   即包里是"空白章"，刷到槽里才被盖章 ⇒ 我方产物必须自己盖（已实现）。

⚠ 同时发现（`device/pass20.out.txt` N3）：**版本头所在擦除块在 +0x200 之后不是空的**（0x3860200 起是有效数据）。
⇒ `switch` 原先"擦整块 + 写 头+0xFF"的做**会抹掉原厂放在同一块里的数据**；
   已改为**读整块→只改前 512 字节→擦→原样写回**（commit 22b114e）。
   这条同时修正了 §风险7 的推论：槽头本身仍是 512 字节（+0x200 起不是头的延续字段，而是同块里的别的用途数据）。

补测（`device/pass21.out.txt`，只读）把这条钉死：

| 绝对地址 | 内容 |
|---|---|
| 0x1C60200（槽 A 头块 +0x200） | `29faf405 78131309 …` 有效数据 |
| 0x3860200（槽 B 头块 +0x200） | **与槽 A 逐字节相同** |
| 0x1C6FF00 / 0x386FF00（头块末尾 256 B） | 两槽同样相同 |
| 0x1C80000（头块的下一块） | 全 `ff`（已擦除） |

⇒ 原厂刷写器把**整个 128 KiB 头块**都写了内容：前 512 B 是版本头，其后约 0x1FE00 B 是镜像自带的数据（两槽一致 ⇒ 来自包，不是运行时状态），再往后才是空块。
⇒ 结论不变但更强：`switch` **必须**读-改-写整块（已实现）；否则回退到原厂时会在原厂槽里抹掉约 127 KiB。
⇒ 我方槽 B 的头块尾部写 0xFF 是安全的：cspboot 只读块首 512 B（内魔数 +0xF4、CRC1 +0xA4），这段尾部数据的作用与它无关。

## 追加核验（同夜）：四个官方包的 extent 字段互推 —— 刷写器是"按头行事"的

同一套字段表解 `升级包/` 里四个官方包（CRC1/CRC2 全部实算一致；包里 `+0x1f0=0 / serial=1 / isNew=0`，
即"空白章"，刷进槽里才被盖章）：

| 版本 | kSize(+0x34) | kFileOff(+0x38) | rSize(+0x40) | rFileOff(+0x44) | body(+0x30) | body == 内核段(进位到 0x40000) + rSize |
|---|---|---|---|---|---|---|
| 4B4 | 0x37fdcc | 0x234 | 0x1600000 | 0x380214 | 0x1980000 | 0x380000 + 0x1600000 ✓ |
| 6B5 | 0x33fdcc | 0x234 | 0x1660000 | 0x340214 | 0x19a0000 | 0x340000 + 0x1660000 ✓ |
| 7B5 | 0x33fdcc | 0x234 | 0x1220000 | 0x340214 | 0x1560000 | ✓ |
| 8B8 | 0x33fdcc | 0x234 | 0x1100000 | 0x340214 | 0x1440000 | ✓ |

三条推论（都还在静态层面，但直接决定需求①能不能走网页）：

1. **`kFileOff/rFileOff` 是"包内偏移"**（`0x234 = 0x214+0x20`，`0x340214 = 0x214+0x340000`），
   而**刷进槽里的活体头这两个值原样不动**（见上表 +0x38/+0x44 仍是 0x234/0x340214）
   ⇒ 刷写器把 body **整段照抄**到槽起点，内核于是落在 `槽+0x20`，rootfs 落在 `槽+(rFileOff-0x214)`，
   头写在 body 之后那一块 —— 与 `docs` 里"头在 body 尾"完全一致。
2. **官方自己的 rootfs 偏移随内核大小变**（4B4 是 0x380000，6B5 起是 0x340000），
   且 `body = 内核段进位到 0x40000 + rSize` 恒等 ⇒ 刷写器**按头里的字段定位**，不是把 0x340000 写死。
   ⇒ 我们把 rootfs 放 `槽+0x800000`（头里写 `rFileOff=0x800214`）在两种解释下都成立：
   照抄 body 的结果 = 头里声明的结果 = 我方 DTS 的结果。
3. **唯一仍未证实的是 cspboot 装载内核的体积上限**：见过的官方内核段最大 0x380000（4B4 的 3.5 MiB），
   H3600 的 OpenWrt 内核实测 ih_size=0x34deac（3.34 MiB），也在这一带。
   ⇒ `tools/release.mjs` 现在会在内核 extent 超过 0x380000 时显式警告（不静默放行）。

## 追加核验（2026-10-14 晚）：两处更正 + 有线吞吐与双核调度的 A 级实测

### 更正 1：本文件上方"我们两条口都只训练到 Gen1 x1"当时是**反的**
`out/cfg-dual.txt`（真机活体 dump，`node out/decode_cfg.mjs out/cfg-dual.txt`）显示我们当时在 **Gen2 x1**：
EP `14c3:7906` 的 PCIe cap 在 **0x80** ⇒ `LnkSta` 在 cap+0x12 = 偏移 0x92，读值 `0x1012`（speed=2 width=1）；
根端口 `1cf2:6830` cap 在 **0x70** ⇒ `LnkSta` 在偏移 130，读值 `0x3012`（speed=2 width=1、DLLLA=1）。
**成因已定位**：本树 `drivers/pci/quirks.c:pcie_failed_link_retrain()`（函数从 94 行起）**没有 Vendor:Device 白名单**
（上游后来收紧成只匹配 ASM2824），枚举根端口时看到 `LnkCtl2.TLS==2.5GT && LnkCap.SLS>2.5GT` 就
打 `removing 2.5GT/s downstream link speed restriction` 并把目标速率抬到 Gen2。补丁 031 之后真机与原厂一致
（EP `0x1011`、根端口 `0x3011`），**但 Wi-Fi 的挂死没变** ⇒ 速率不是病因（详见 02 文 §P.4）。
⚠ 偏移 0x12 在**头里**是 **BAR0 的高半**（读到 `0x1030` = `0x10300000` 的上 16 位），不是 LnkSta —— 别再拿它当链路证据。

### 更正 2：MPS/MRRS 那条"没在真机读过"现在读过了，假设可以关掉
我们侧 `DevCtl`：EP `0x291f`、根端口 `0x201f`；原厂 EP `0x2910`。
按 `pci_regs.h` 逐位算（MPS=bits[7:5]、MRRS=bits[14:12]、RO=bit4、ExtTag=bit8、错误上报=bits[3:0]）：
**MPS=128 B、MRRS=512 B、RO=1、ExtTag=1 两边完全相同**，唯一差别是我们的四个错误上报使能位为 1
（`pcieport … AER: enabled` 所致），`DevSta` 全零，`Command` 两边都是 `0x0146`。⇒ MPS/MRRS/ExtTag 失配**排除**。

### A 级：有线吞吐（1 Gbps link up 的 `lan1`，主机 192.168.1.177）

| 测法 | 值 | 一手出处 |
|---|---|---|
| 设备 HTTP 拉 200 MiB，单流 | 6 s ⇒ **≈273 Mbit/s** | `out/tput-rx.log` |
| 同上 1 / 2 / 4 并行流 | **279 / 305 / 305 Mbit/s**（加流不涨 ⇒ 不是并发问题） | `out/tput-scale.log` |
| 以太网 IRQ 钉到 CPU1 后单流 | **279 Mbit/s**（`NET_RX` 确实跟着搬：282 → 6909） | `out/tput-scale.log` |
| 设备→主机灌 TCP | ≈190 Mbit/s（单次样本，**当时没落日志文件**，别当精确值） | 会话内测量 |

原因是驱动侧的，不是配置的（`ethtool -k/ -l / -c lan1` 原文在 `out/irq-audit.log`）：
`rx-checksumming off [fixed]`、`tx-checksum-ip-generic off [fixed]`、`tx-scatter-gather off [fixed]`、
`tx-tcp-segmentation off [fixed]`、`receive-hashing off [fixed]`；ring/coalesce 参数 `Not supported`
⇒ **单 RX 队列、无 RSS、无校验和卸载、无 TSO**，软件 GRO 是唯一开着的卸载（`hw-tc-offload: on` 只是声明位，驱动有没有实现未查）。

### A 级：不是"只跑单核"，但网络栈确实只在一个核上
`out/net-audit.log`：`possible=present=online=0-1`，两个 `ARMv7 Processor rev 1 (v7l)` 都在累积 tick
（`cpu0 1742 … / cpu1 1731 …`），IPI 的 resched/function-call 两边都有计数 ⇒ **SMP 是活的**；
`CONFIG_CPU_FREQ` 无（`cpufreq=none`，两个核都跑固定主频）。
但 `irq 30 = 92000000.ethernet` 计数全在 CPU0，`NET_RX` 软中断 `14150 : 282`（`out/irq-audit.log`）
⇒ 默认全部收包处理压在 CPU0；把中断亲和改到 CPU1 只是把活搬过去，吞吐没变（见上表）⇒

`nf_flow_table`/硬件 offload 是否真把桥接流量卸在 SoC 里。要判"能不能跑满千兆"必须再加**一台有线机器**。
镜像里有 `/usr/bin/iperf3` 可直接用。
