# 有线吞吐测量记录与方法（2026-10-29）

## 结论

在这套测试条件下，**没有任何一个数字能代表盒子以太网口的真实上限**，因为每一条路径的另一端都是"1GHz Cortex-A9 上本地终结 TCP"的设备，而本地终结流量不过 PPE，全靠 CPU：

| 路径 | 结果 | 实际瓶颈 |
|---|---|---|
| PC ↔ 盒子（iperf3，1/4/8/16 流） | 161 / 282 / 288 / 277 Mbit/s | **PC 的 USB 网卡**：RTL8153 挂在坞内 USB2.0 Hub（GL852，父链实证）→ 480Mbps 总线，实测顶 ~300M |
| 盒子自己下百度 CDN（4 流 HTTPS） | 149 Mbit/s，CPU 98% | 盒子自身 TLS 用户态开销（mbedtls 在 1GHz A9） |
| 主路由（同款 E2631，原厂 4.1）从盒子下载 8×16MB | 134 MiB / 8 s = **140 Mbit/s** | 主路由自身：本地终结 TCP，无加速 |
| 盒子 WAN 链路 | 1000M full，rx/tx/CRC 错误 **0**，丢包 0 | — |

**PPE 硬件转发只对"穿过盒子"的流量生效**，对投递给盒子本机或由盒子发起的流量没有任何作用。因此判断"盒子以太网行不行"必须看链路层与转发场景，而不是端点吞吐。

## 可用的证据（已具备）

- 链路：`/sys/class/net/wan/speed = 1000`，`duplex = full`，`rx_errors = rx_crc_errors = tx_errors = 0`；
- 端点吞吐与 CPU 的关系自洽：盒子自身 282M 时 CPU 45%，149M TLS 时 CPU 98%——都不是链路饱和；
- 多流不涨（1→16 流 260–288M）→ 端点侧单一资源受限，非链路拥塞。

## 要拿到真实上限所需的条件

一台**不是 1GHz A9、且网卡不在 USB2.0 总线上**的对端，且流量必须**穿盒**：

```
[客户端: 盒子 LAN 口] → 盒子(NAT/PPE) → 盒子 WAN → [服务端: 主路由侧]
```

单机（PC 直连盒子 WAN）只能测"盒子自己收发"，永远过不了 PPE。

## 旁证：v1.3 的 ≥395 Mbit/s 是哪来的

那次是 PC 在盒子 LAN 侧、对端在公网（OPPO CDN），流量**穿过盒子** → PPE 接管，CPU 7%、WAN 软件计数不动。这正是本记录缺的那一环。

## 附带发现（非本项目固件问题）

- 原厂 E2631 的 busybox wget 下载 **64MB** 文件时会在 ~100KB 处停住，4MB/16MB 均正常——同款 SoC 的原厂 4.1 TCP 栈在大文件长连接上的行为，仅记录，不影响我方。
- 厂机 httpd docroot 在只读 squashfs（`/home/httpd/public`），`/var` 为 40MB tmpfs，无法直接投放测试大文件。
- 厂机 busybox 无 `nc/httpd/iperf3`，只有 `wget`/`cat`。
