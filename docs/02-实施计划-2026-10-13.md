## 阶段 1 · 格式验证：重封官方包，经 `supgrade.html` 直刷（用户选的第一步）

目的：把"包格式能不能被接受"这个变量，从"OpenWrt 能不能跑"里彻底剥离出来。

1.1 工具 `tools/mkfactory.mjs`（纯 Node，本机可跑，也在 CI 里可跑）：
    - 输入：**模板 = 8B8 官方包**（最新、key `0x1351/0x5211`、无版本门），kernel extent，rootfs extent；
    - 布局：`[16 外魔数][4 hdr_ofs=0][512 verhdr][32 槽标记][kernel][0x214 零填充][rootfs]`；
    - 填 `+0x34/0x38/0x3c`(kernel size/包内偏移/CRC) 、`+0x40/0x44/0x48`(rootfs 同) 、`+0x30 = ROUND_UP(body_len, 0x20000)`；
    - **载荷一律明文，CRC 对"实际存放的字节"算**（kernel 明文 CRC 明文；rootfs 我们写明文 ⇒ CRC 对明文算）；
    - 重算 `+0xa4 CRC1 = CRC32(hdr[0:0xa4])`、`+0x1fc CRC2 = CRC32(hdr[0:0x1fc])`；
    - **`+0x1f0/0x1f4/0x1f8` 保持模板原值不盖章**（serial 由原厂刷写器写 `max+1`，我们不该预填）；
    - `+0x8c` 保持 0（绝不动 bootloader）；`+0x1e0..0x1ec` 槽表保持 `{0x700000,0x2300000,0x2300000,0x3F00000}` 不改；
    - **不追加任何 fwtool metadata**（`IMAGE/*` 链里不要 `append-metadata`）；文件必须正好停在头部声明的位置。
    - 自校验：写完立刻重读，逐条 assert 四个 CRC + 边界（照抄 cnjn `mkfw.py` 末尾的 4 条 assert）。
1.2 **第一次实验的载荷就是官方 8B8 自己的 kernel+rootfs**（即"只重打包不改内容"）。
    预期：Web 页接受 → 刷进**非活动槽**（槽 B）→ 重启后跑的是原厂 8B8。
    这一轮同时验证五件事：外层魔数接受度、CRC1/CRC2 算法、key 门（`1351/5211`）、8B8 的 `+0x110=V1.1.1` 会不会被硬件版本门拒、
    以及**刷写器是否真的只写非活动槽**（读 `versionstates` 的 `curverBootStartPhyAddr` 前后对比）。
1.3 失败矩阵（预设判据，不靠猜）：
    - 页面报"文件无效/不是本机固件" → 查产品串与 `BitVidMap`（7B5=`0x07`、8B8=`0x0F`）与 vid=63 的关系；
    - 报"版本不高于当前" → 换模板为 7B5 并把版本串写成高于账面（注意原厂 `BootVer` 串格式是 `V%04u.%04u.%04u`，每段 ≤9999）；
    - 报 CRC/校验失败 → 用 `tools/verify_hdr_crc.mjs` 对我方包逐字段对拍；
    - **任何情况下**：槽 A 是原厂且 serial 不低于槽 B，刷坏了是 A/B 回退，不是砖；串口 bootmenu（密码 `5cE080@fyBD`）仍可指槽；编程器兜底。

门禁：**Web 直刷成功 + 系统从被刷槽启动 + 槽 A 未被改动**。

## 阶段 2 · 上真正的 OpenWrt 载荷（先 RAM 后 flash）

2.1 串口 TFTP 先跑 initramfs（**不写 flash，零砖险**）：验证 SPI-NAND 能读、`eth0/eth1` 有 carrier、mt7916 起卡、第二核上线。
2.2 **PHY/MDIO 拓扑实测**（这是"完整 AP"验收的前置，也是唯一不能靠文档的地方）：
    - 扫 MDIO `0x9a101000` 上 0..31 号地址的 ID1/ID2/BMSR（可绕过设备树直读寄存器，参考 WorkBuddy 的 `probe-e2631.sh` 的 `mdio` 段思路）；
    - 与 `0x84b95011`(ZX5201) 比对，判定 E2631 到底用不用外部 PHY；
    - 逐个插网线看哪个 `eth*/gmac_port` 有 carrier，把 **面板 LAN1/LAN2/LAN3 / WAN ↔ gmac portN ↔ phy 地址** 定死；
    - 顺带把 MAC 来源定死（H3600 是 `tag@0x100000` 偏移 `0x1e` 取 6 字节、`mac-base` nvmem，2.4G=+2、5G=+3；E2631 必须自己验）。
2.3 打 OpenWrt 载荷包（kernel 明文 uImage + squashfs rootfs 明文），经 Web 刷进槽 B。
    内核体积预算：官方 kernel extent 是 0x33FDCC(3.4 MB)，但**真上限是槽跨度 28 MiB**（`+0x30` 会随 body 自动重算），
    所以不裁内核；但要注意 **cspboot 从 flash 加载内核是否有堆拷贝上限**（SR1010 是 ~8 MiB，E2631 未测）——
    先用一个"故意超大"的 initramfs 探一次，找出真实上限，再定 squashfs 的预算。
2.4 rootfs 呈现方式：照 cnjn 的做法写一个 `zte-zx279128s-rootfs`，把槽内**跳过坏块后的连续好块**拼成一个虚拟 `rootfs` MTD，
    配 `CONFIG_CMDLINE_FORCE` 的 `root=/dev/mtdblock<N> rootfstype=squashfs ro rootwait`（原厂 U-Boot 会自己塞 `root=`，必须 FORCE）。
    原厂有 `CONFIG_CSPKERNEL_MTD_SKIPBAD=y` 正是这套机制的对应物。

门禁：**从 flash 启动进 OpenWrt，WAN+LAN 全通，双频 Wi-Fi 起卡并跑 iperf**。

## 阶段 3 · 需求②：`e2631-fwslot`（从 OpenWrt 退回原厂）

以 `refs-cnjn/zte-fwslot/src/zte-fwslot.c`（741 行）为蓝本，**只改常量、不改逻辑**：

| 处 | SR1010 | E2631 |
|---|---|---|
| `slot_start[2]` | `{0x600000,0x2f00000}` | **`{0x700000,0x2300000}`** |
| `UBOOT_SIZE` | `0x180000` | **`0`**（E2631 包里不含 bootloader，`+0x8c=0`；同时删掉 `r[0]` 那条 U-Boot CRC region） |
| `KERNEL_MAGIC_SIZE` | 32 | **32（保留）**——实测槽首就是那 32 字节标记，uImage 在 `+0x20` |
| `PRODUCT` | `"ZXSLC SR1010"` | **`"ZXHN E2631 V1.0.0"`** |
| `SLOT_SIZE` | `0x2900000` | `0x1C00000`（仅用于容量报错门限） |
| 栈上 `pad[0x20000]/blk[0x20000]` | 128 KiB | 同（E2631 erasesize 也是 128 KiB）；建议改 malloc 更稳 |
| `running_slot_offset()` | `/sys/firmware/zx279133/slot_offset`（自研 bootinfo 驱动） | **改读 `/proc/cmdline` 尾部 U-Boot 传的 7 段串第 4 段**（真机实测 `... U-Boot V1.0.0 20250325110003 0x700000 0x0 0xaf 0xa3`）；取不到就报错退出，**不猜** |
| `slot_scan / max_serial / next_slot / 擦块再整块写 / switch 前先 slot_verify` | — | **一字不改照抄** |

回退语义（比 cnjn 更小爆破半径）：
- `e2631-fwslot boot-stock`：把**我方槽**（槽 B）头部的 `+0x1f4 serial` 改成 `0`，重算 CRC2，擦那个 128 KiB 块后整块写回。
  规则是 `slot0.serial < slot1.serial || slot0.serial==0 → 起 slot1，否则起 slot0；相等起 slot0`，
  槽 A serial=`0x10` > 槽 B `0` ⇒ **起槽 A（原厂）**，且**完全不动原厂槽的任何一个字节**。
- `e2631-fwslot boot-owrt`：serial 改回 `max+1`。
- `e2631-fwslot info [-j]` / `check` / `flash` 保留。
- **绝不使用原厂 `fw_flashing -v switch`**：它不擦除就地写，NAND 只能 1→0 ⇒ 新旧按位与、serial 不变大、CRC2 报废，
  且错误判断反了（`CspUserMtdWrite` 失败返回 1，调用方把 `>=0` 当成功）、写完不回读。
- **`/proc/zte/verinfo/versionstates` 是开机快照**，写完 flash 不更新 ⇒ 工具的"写后确认"必须重读 flash，不能读它。

先跑 cnjn 的 `fakemtd` LD_PRELOAD 测试套件（改成 E2631 偏移），**再上真机**。
门禁：`.5` 上完成 OpenWrt → 原厂 → OpenWrt 两轮往返，且每轮都能进系统。

## 阶段 4 · 收尾为可用 AP

- `board.d/01_leds`、`02_network`（按 §2.2 实测结果，3 LAN + 1 WAN）、UCI 默认、`gpio-keys-polled`；

## 风险清单（按会咬人的程度）

1. **cspboot 从 flash 加载内核的体积上限未知**（SR1010 ~8 MiB；E2631 未测）。§2.3 必须先探。
2. **JFFS2/squashfs 在带片上 ECC 的 SPI-NAND 上的同页二次编程坑**：cnjn 撞过 `error -74`，
   解法是内核 `program_once` 补丁 + cleanmarker 移到数据区（每块损失一页）。E2631 的 HYF1GQ4UTACAE 同类器件，**极可能同样需要**。
3. **按键中断模式会把机器锁死**：H3600 参考 DTS 明确写了"用 `gpio-keys` irq 模式实测触发 RCU stall/整机锁死"，
   原因是 `zx279133-gpio` IRQ chip 未在真机验证 ⇒ E2631 **一律 `gpio-keys-polled`，`poll-interval=<50>`**。
4. **L2C 少一条属性就死锁/读到脏数据**（见 §0.4）。
5. **U-Boot 选槽不回落**：选中的槽起不来不会自动换槽（cnjn 实测）⇒ 任何自测前必须确认"另一个槽 serial 不低于我方"。
6. **软浮点**：`CPU_TYPE:=cortex-a9` 默认带 VFP 会产非法指令；toolchain/kernel/userland 三处都要一致地关。
   另外 Go 类包（dae/tailscale 等）在 armv7 无硬件除法 + 无 AES 指令的机器上性能很差，选包要克制。
7. **`0x1f0/0x1f4/0x1f8` 之外可能还有原厂用的字段**：cnjn 包里 `hdr+0x08 = 0x510`（他文档没解释，
   第三方在槽里观测到的记录长度也是 `0x510` 而非 `0x200`）⇒ `switch` 擦整块会把 `0x200..0x510` 抹成 FF。
   **E2631 上必须先用只读转储确认槽头是否长于 512 字节**，否则我的"擦块+整块写"会破坏未知字段。
   （这一条直接决定阶段 3 的实现细节，优先验。）
8. **telnet 会话数有限**（"The connect number is limited"），且失败 3 次锁 60 s ⇒ 真机取证要单会话、批量化。

# 追加（2026-10-13 深夜）：本轮实际落地的决定

## A. 风险清单的结案情况

- **风险 7（槽头是否长于 512 B）— 已结案，且对 E2631 不成立。**
  真机读 `backverheaderaddr = 0x3860000`：`+0x08/+0x0c = 51 13 / 11 52` 就是
  `versionstates` 里的 `curUpgradeKey1/2 = 0x1351/0x5211`，即该字段在 E2631 上是**升级 key 对**，
  不是 cnjn 在 SR1010 上看到的 `0x510` 记录长度；`0x200` 之后在编程器固件里全 FF。
  ⇒ `switch` 的"擦整块 + 整块回写（0xff 填充）"不会破坏任何已知字段。
- **风险 2（JFFS2 同页二次编程）— 已经带上补丁，不再是未知。**
  从 cnjn 的 6.18 树取 `0c3602121`（`mtd_info.program_once` + JFFS2 把 cleanmarker 放进数据区）
  与 `8aa6f4607`（扫描别把整块重读一遍），落在
  `build/overlay/target/linux/sanechips/patches-6.18/029,030`；
  已对 kernel tag **v6.18** 原文件 `git apply` 演练通过（029 有一处 -168 行偏移）。
  另加 fstools `203-overlay-ram-fallback`（overlay 挂不上时退到 RAM overlay 而不是停在只读根），
  针对本树 pin 的 fstools `2aa16407fd` 重新生成上下文后演练通过。
- **新发现的硬约束（风险 9）：必须强制内核命令行。**
  真机 `/proc/cmdline` = `... root=/dev/mtdblock8 rootfstype=jffs2 init=/bin/sh -c "exec /bin/sh"; U-Boot V1.0.0 20250325110003 0x700000 0x0 0xaf 0xa3`。
  原厂 U-Boot 把**它自己的** root/init 交给内核，直接刷 OpenWrt 会挂不上 root、PID 1 变成 shell。
  ⇒ `apply.sh` 往 `target/linux/sanechips/config-6.18` 追加
  `CONFIG_CMDLINE_BOOL=y / CONFIG_CMDLINE="… root=/dev/mtdblock7 rootfstype=squashfs ro rootwait" / CONFIG_CMDLINE_FORCE=y`
  （mtd7 = 我方 DTS 的 `rootfs`；OpenWrt 基线里 `CONFIG_MTD_PARTITIONED_MASTER` 是关的，mtd0 就是第一个分区）。
  代价：这个改动是 **per-target** 的，被 overlay 过的树只应编 E2631，不要再拿它出 H3600 的镜像。
  顺带确认：命令行尾部的 `U-Boot … 0x700000 …` 第 4 个十六进制数就是**当前槽基址**，
  `e2631-fwslot` 用它判断"我在哪个槽"，这条解析与真机样本一致。
- **风险 10（坏块让固定偏移失效）— 本机已排除，工具里留了守卫。**
  `/sys/class/mtd/mtd0..14` 的 `bbt_blocks` 与 `bad_blocks` **全为 0**，dmesg 无 bad/bbt 行
  ⇒ 这台机器没有坏块，"rootfs@slot+0x800000 / 版本头@slot+0x1000000 / rootfs_data@+0x1020000"成立。
  换一台不成立，所以 `e2631-fwslot flash` 在擦除**之前**检查 `[槽起点, body 末尾+1 块)` 的坏块表，
  有坏块就拒绝写入（不是写完再报错）。

## G. 阶段 3（OpenWrt 里再升级）的做法已定，抄 cnjn 的骨架、改一处语义


```sh

platform_do_upgrade()  { zte-fwslot flash "$1" || { ...; return 1; }; }
```

E2631 照搬这个骨架，但有一处**语义必须不同**：

stage2 跑在 RAM 里，擦自己的槽是安全的。⇒ `e2631-fwslot` 需要一个显式目标（`flash -s <slot>` 之类），
这一步等第一次开机验证通过、确认 `switch` 回退可用之后再补，不在本轮。

### I.2 ofpart 的真实规则（读了 v6.18 源码，不是二手资料）
v6.18 里解析器已搬进 `drivers/mtd/parsers/ofpart_core.c`（缓存：`out/ofpart_core.c`）。`parse_fixed_partitions()`：

- master（`!master->parent`）取 `of_get_child_by_name(mtd_node, "partitions")`；命中
  `parse_ofpart_match_table`（含 `fixed-partitions`）时 `dedicated = true`；
- `dedicated` 时遍历该容器的**全部**子节点，`parts[i].offset = of_read_number(reg, a_cells)` ⇒ **绝对** flash 偏移，
  既不查重叠也不要求递增；
- 只有 *分区节点自己* 带 `compatible` 时才是子分区语义，那时偏移是相对的（`mtdpart.c` 的 `allocate_partition`）。

⇒ 我们的"扁平重叠表"（`slot0`/`slot1` 与 `rootfs`/`slot1-header`/`rootfs_data` 并存、绝对地址）是合法用法。
前提是 `partitions` 容器里只能有分区子节点：`nvmem-layout` 挂在 `partition@100000` 里面，不在容器里 ⇒ 不会被子节点计数吃掉。

### I.3 `verify_img.mjs` 自己在一份真 dtb 上露了两个洞（都已修）
测试样本用的是 `_scratch2/sx/sysupgrade-zte_zxhn-h3600/kernel`（H3600 真镜像，尾部附 `.dtb`）。

1. **根节点被当成子节点**：`fdtParse()` 预置了一个空 root，于是流里第一个 `BEGIN_NODE`（真正的根）成了它的孩子
   ⇒ `model`、`memory`、`cpus` 全部"查不到"，表现为 FAIL/"no memory node"。改成第一个 `BEGIN_NODE` 就是根。

   `sval()`（单值串在第一个 NUL 处截断）和 `cval()`（`compatible` 是 NUL 分隔的串列表，必须整表参与匹配）。

   证据：修好后同一份 H3600 dtb 立刻报出 `//soc/usb@9100000 [zte,zx279128s-dwc3]` 是 enabled ⇒

   （`zte,zx279128s-smp`），第二核的疑问静态结案。

### I.10 需求②在静态复核里暴露的真 bug（已修，run 17 带上）

`e2631-fwslot` 判断"现在跑在哪个槽"只看 `/proc/cmdline` 里原厂 U-Boot 的尾串
（`… U-Boot V1.0.0 <日期> 0x700000 0x0 0xaf 0xa3`）。但我们自己的内核用
`CONFIG_CMDLINE_FORCE` **把那条命令行整个换掉了** —— 也就是说，**最需要 `switch` 的那个系统（OpenWrt）
恰好读不到这个尾串**，`switch` 会直接报 "cannot tell which slot is running" 而失败。
这不需要真机就能推出来，但只有在把需求②的执行路径逐步过一遍时才会被发现。

修法（`3a1fdf8`）：

1. 尾串不存在时，退回到"根文件系统所在分区的 sysfs offset"（`/sys/class/mtd/mtdN/offset` 对分区就是
   **绝对 flash 偏移**，内核 `mtdpart.c` 的 `offset_show()` 直接输出 `mtd->part.offset`）：
   我方镜像里 `rootfs` = 0x2b00000 ⇒ 落在 slot1 ⇒ running=1 ⇒ `switch` 抬升槽 A 的序号 ✓；
   原厂镜像里 `rootfs` = 0xA40000 ⇒ 落在 slot0 ✓（两条路都对）。
2. 这个回退**只在我方镜像上启用**：判据是存在整槽分区 `slot0`。原厂分区表只有一个写死的 `rootfs`，
   它说明不了 cspboot 实际选了哪个槽；而整槽分区只存在于我们的 DTS 里。
3. `slot_index()` 由"相等"改成"落在区间内"（rootfs 不在槽起点）。
4. 顺手把"槽 A 永久保留原厂"变成硬约束：`flash` 若算出目标是 slot0 就直接拒绝
   （从 OpenWrt 里误跑 `flash` 会抹掉唯一的安全网）。

⚠ 影响：**run 15 的产物（`8d27975`）里那个 `e2631-fwslot` 没有这个修复**，刷入请用 run 17
（`38323365275`，`3a1fdf8`）的 artifact 重新跑一次 `node tools/release.mjs --run 38323365275`，

## L. 启动失败的根因结案：cspboot 自己算 rootfs 落点（2026-10-13 下午，串口日志为证）

### L.1 串口把槽 B 判坏的逐行证据（`device/serial-slotB-rejected.log`）

```
pdt_getreal_kernelfs:461 ... kernle@2300000[ 34bdf8 ] fs@ 2660000[ 800000 ] header:3300000
zteboot_update_bootpara:675 JffsOffset:0x800214,JffsSize:0x800000   ← 头里的 rFileOff/rSize
pdt_getreal_kernelfs:570 check fs: start:2660000                     ← 实际用的落点
csp_crc ... data addr:423a0000, crc_len:0x800000  crc=0x62686622, 0x9d9799dd
zteboot_verify_fs:213 Romfs CRC check failed. ... Real crc 9d9799dd, Want c2379b2d
pdt_getreal_kernelfs:582 not found vaild fs!!
pdt_start_kernel:747 Total found 2 firmwares(valid:1), start from ver 0
```

`0x2300000 + ceil(0x34bdf8 / 0x20000) * 0x20000 = 0x2300000 + 0x360000 = 0x2660000` —— 与日志一行不差。
**cspboot 定位 rootfs 用的是"槽起点 + 声明内核大小向上取整到擦除块"，头里的 `rFileOff` 只是给人看的**。
`Want c2379b2d` 正是我们 squashfs 的正确 CRC（旧包里算对的那个），只是它去错了地址。

### L.2 官方四个包都满足同一条恒等式（本轮新查，`node build/tools/mkfactory.mjs` 现场跑）

| 包 | `kSize` | `ceil(kSize/128K)` | 头里 `rFileOff` | `0x214 + ceil` | 恒等式 |
|---|---|---|---|---|---|
| 4B4 (2023) | 0x37fdcc | 0x380000 | 0x380214 | 0x380214 | 成立 |
| 6B5 (2024) | 0x33fdcc | 0x340000 | 0x340214 | 0x340214 | 成立 |
| 7B5 (2025) | 0x33fdcc | 0x340000 | 0x340214 | 0x340214 | 成立 |
| 8B8 (2026) | 0x33fdcc | 0x340000 | 0x340214 | 0x340214 | 成立 |
| **我方旧包** | 0x34bdf8 | 0x360000 | **0x800214** | 0x360214 | **破坏 ⇒ 起不来** |

于是 §K.5 留的那个问号现在有答案了：**rootfs CRC 不合格时 cspboot 会判该槽无效并回落到另一槽**（日志里
`valid:1 ... start from ver 0`），这一类失败不会变砖。内核段 CRC 不过同理（`verify kernel success!!` 之后才看 fs）。

### L.3 修法：把"推导落点"钉死成常数，而不是迁就内核大小

包侧（`build/tools/mkfactory.mjs`）：给了 `--rootfs-at` 时，**声明的内核段 = 整个填充区** `kSize = ROOTFS_AT - 32`，
`kCrc` 覆盖"uImage + 其后的 0x00 填充"（填充本来就是我们写进 flash 的字节，CRC 覆盖它才自洽）；
并加了三处硬校验：`assemble()` 里 `up(kSize) != rootfsAt` 直接 die、pack 后自检新增 `derivedFsOff ok`、
`tools/verify_pkg.mjs` 新增独立断言"rootfs sits where cspboot derives it"。

几何定稿（槽内相对 → 槽 B 绝对）：

| 区 | 槽内偏移 | 绝对（slot1=0x2300000） | 大小 |
|---|---|---|---|
| 槽标记 + 内核（填充到整区） | +0x000000 | 0x2300000 | 0x400000 |
| squashfs（填充到整区） | +0x400000 | **0x2700000** = mtd7 `rootfs` | 0x800000 |
| 版本头块 | +0xc00000 | **0x2f00000** = mtd8 `slot1-header` | 0x20000 |
| overlay | +0xc20000 | **0x2f20000** = mtd9 `rootfs_data` | **0xFE0000 = 15.875 MiB**（比旧方案多 4 MiB） |
| 包文件 | — | — | `0xC00214` = **12,583,444 B**（比旧包小 4 MiB，上传更快） |

`KERNEL_SIZE` 从 8192k 降到 **4096k**：`check-size` 比的是 `32B 标记 + uImage`（`limitsize >= imagesize`，
`include/image-commands.mk:316`），4 MiB 正好等于内核区上限 —— **内核长过 4 MiB 就在构建里失败，
而不是悄悄把 rootfs 推到分区表之外的地址**（就是这次的事故模式）。当前内核 0x34be18 ⇒ 还剩 0xb41e8 余量。

### L.5 LED：两次采样互相矛盾，且这次证明无法在原厂系统里测

`/proc/zte/ledkey_m/led` 的两个时刻（同一台、同一版固件）：

| 采样时刻 | `0x32`/gpio8 | `0x64`/gpio40 | `0x128`/gpio60 |
|---|---|---|---|
| 开机 3 分钟（189 s，重启后） | off | **on** | off |
| 稳定运行一小时后 | off | off | **on** |

U-Boot 侧：`output gpio:8,value:1`、`output gpio:40,value:1`、`output gpio:60,value:0`。
⇒ 40 是"最早亮起来"的那颗（更像电源灯），60 是"稳定后才亮"的那颗（更像 internet），8 两次都没亮过。
极性仍判不了：**想读 GPIO bank 寄存器（`0x94407000+0x40n`，DIR@+0 / DATA@+0x14）直接把整机搞挂了** ——
见 L.6。DTS 现按"40 = power，ACTIVE_HIGH，`default-state=on`"写，并把上面这张表和"首启看面板，
灯不亮就翻极性 / 与 60 对调"的判断依据写进注释；`led-boot/led-running/led-failsafe/led-upgrade` 四条别名都指它，
所以这件事错了只是状态灯不动，**不是启动风险**。

### L.6 一次我造成的设备重启（如实记录）

下午为了定 LED 极性，在原厂 shell 里用 `devmem2` **只读** `0x94407000/40/80/c0/100/140` 六个 bank 的
DIR/DATA/SET/CLR。命令发出后 telnet 立刻 ECONNRESET，重连后 `cat /proc/uptime` = **189.13 s** ⇒ 板子重启了。
即"从原厂系统读 ZX279128S 的 GPIO bank 寄存器会把总线打挂、由看门狗复位"——和之前 MDIO 寄存器写挂是同一类坑，
**只读也算危险动作**。后果核对：没有写任何 flash 设备，槽 A 仍是原厂 7B5，`ledkey_m` 里那颗亮着的灯与重启前一致，
设备已正常提供网络。**教训并入既有记忆：极性/引脚这类"看面板就行"的事实，不要为了拿寄存器证据去碰原厂寄存器。**

## O. 首启实测（run 21 镜像，19:0x 本地）与两条推翻设计假设的结论

**起来了**：procd 为 1 号进程、`root=/dev/mtdblock7` 挂上 squashfs、jffs2 overlay 挂载、
`lan1: Link is Up - 1Gbps/Full`、br-lan 192.168.1.1/24 发 DHCP、ssh 进得去、
`MemTotal 248 MB`、双核（`migration/0`+`migration/1`）、`VFP` 无（armv7l 软浮点用户态正常跑）。

| 猜过的东西 | 实测结果 |
|---|---|
| MDIO 上 4 个内部 GEPHY 在 `0xa..0xd` | **对**：`9a101000.mdio:0a/0b/0c/0d` 全部应答，驱动 Generic |
| 端口 netdev 名字来自 DTS `label` | **对**：`lan1/lan2/lan3/wan` 如期出现（`zx279128s-main.c:1313` 用 `strscpy(netdev->name, label)`） |
| 以太网驱动内建 | **对**：`CONFIG_ZX279128S_ETH=y`、`MDIO_ZX279128S=y`、`PHY_ZX279128S_PCIE=y` |
| jffs2 补丁 029 生效 | **对**：`jffs2: NAND pages can be programmed once: clean markers are in the data, 2048 bytes` |
| ECC/坏块 | `bad=0 ecc_fail=0`，`corrected` 有值（片内 ECC 正常纠错） |
| 三色灯单灯 | **对**（见 §L.5 与后续扫灯）：40=绿、60=红、8=蓝，全 ACTIVE_LOW |
| 端口 MAC 来自 nvmem | **错**：没人引用 `macaddr_tag_1e` ⇒ 四个口随机 MAC，已修 |

**结论一（会毁掉持久化的那条）**：内核把 squashfs 之后的块自动切成 `rootfs_data` 给 overlay 用
（`1 squashfs-split partitions found on MTD device rootfs`，实测 mtd8 = `槽+0x840000` 长 `0x3c0000`），
而我们头里 `rSize=0x800000` 把这段算进了 cspboot 的校验窗口 ⇒ **第一次保存配置就毁掉本槽 CRC**；
设备侧 `e2631-fwslot info` 自己报出 `damaged: root filesystem CRC mismatch`、`[next boot]` 落回槽 0。
修法：`rSize = ceil(squashfs/128K)`，校验窗口与可写区不再重叠；DTS 删掉自己声明的 `rootfs_data`
（否则同名分区会被 fstools 优先选中），版本头块加 `read-only`。

**结论二（推翻"自动回退可靠"的假设）**：`reboot` 在这台机器上**卡死**。实测发完 `reboot`，
160 秒内 `192.168.1.1:22` 与 `192.168.5.3:23` 双双无响应 —— 因为 `syscon-reboot` 没有设备
（topcrm 是 `CLK_OF_DECLARE` 注册的，`of_clk_init()` 先把它标成 OF_POPULATED，
`of_platform_bus_create()` 遇到已标记节点**不再向下建设备**，于是 `phy@0/phy@1/reboot` 三个子节点全空）。
连带影响：`/sbin/e2631-trial` 的十分钟保险只能改槽位标记，**最后一步重启仍需人工断电**。
修法见 §N 的 DTS 第二句点；刷机后必验项第一位就是"reboot 能不能真重启"。

### P.2 冷启动那一次下载到底卡在哪（新工具与读数）

不刷机就能读 MT7916 的内部寄存器：`out/regprobe/regprobe.c`（29,140 B，vermagic `6.18.55 SMP mod_unload ARMv7 p2v8`，
sha256 `34ccd4b8…46d1`）。要点三条，都是踩出来的：
1. 冷卡的 `Command=0x0140`（MSE 还没置），不显式 `pci_write_config_word(... | PCI_COMMAND_MEMORY)` 的话
   **每次 MMIO 读都返回 `0xffffffff`**，看起来和链路死掉一模一样；
2. 读 `MT_TOP_MISC`（`0x180600f0`）必须先写芯片的 L1 remap：`BAR0+0xfe260 = 0x1806`，再读 `BAR0+0xe00f0`，
   `FW_STATE = bits[2:0]`（0 INITIAL / 1 FW_DOWNLOAD / 2 NORMAL_OPERATION / 3 NORMAL_TRX / 7 RDY，`mt76_connac_mcu.h:1098-1102`）；
3. 采样必须避开驱动正在 probe 的时刻 —— 双方写同一个 remap 寄存器，交错只出噪声。

读到的事实（`out/cold-fs.log`、`out/cold-ladder.log`）：**上电后、从没绑过驱动时，MMIO 读得动，`FW_STATE=0`（INITIAL）**，
`0x790a` 那个功能也是 `0`。⇒ 卡住前总线是活的，死的是"第一次下载"这个动作本身；
绑上去之后 ssh 当场 `Connection reset by peer` 并再无响应。
另外确认过"脏卡"效应：一次硬挂之后无论用我们的还是原厂 blob，重绑都变成 `-EIO`（`Timeout for initializing firmware`），
**软重启清不掉**，只有真断电（PERST）能清。

### P.3 有线吞吐 / CPU / 中断（2026-10-14 实测）

先回答"是不是只跑在单核上"：**不是只跑一个核，但网络全在一个核上。**
`out/net-audit.log`：`possible/present/online` 都是 `0-1`，两个核都在累积 tick，IPI（resched/function-call）两边都有；
但 `irq 30 = 92000000.ethernet` 的计数全在 CPU0，`NET_RX` 软中断 `14150 vs 282`（`out/irq-audit.log`）。

| 测法 | 结果 | 出处 |
|---|---|---|
| 设备从主机拉 200 MiB（HTTP，单流） | 6 s ⇒ ≈273 Mbit/s | `out/tput-rx.log` |
| 同上 1/2/4 并行流 | 279 / 305 / 305 Mbit/s（**加流不涨**） | `out/tput-scale.log` |
| 把 eth IRQ 钉到 CPU1，单流 | 279 Mbit/s（`NET_RX` 确实跟着搬到 CPU1：282→6909） | `out/tput-scale.log` |
| 设备往主机灌 TCP（上传） | ≈190 Mbit/s，**单次样本、没存档日志**（当时 busybox `nc` 拒 `-N/-w`，第一次数还错了一档） | 结论级：别当精确值用 |

**为什么跑不满千兆**（已证据化的三条 + 一条未排除）：
1. `zx279128s-eth` **没有任何卸载**：`rx-checksumming off [fixed]`、`tx-checksum-ip-generic off [fixed]`、
   `tx-scatter-gather off [fixed]`、`tx-tcp-segmentation off [fixed]`、`receive-hashing off [fixed]`，GRO 开着（软件），
   `ethtool -l/-C` 都不支持 ⇒ 单 RX 队列、无 RSS、CPU 算校验和；
2. 单核 softirq 上限就在这附近 —— 但**把中断挪到 CPU1 没有提升**，说明瓶颈不是"那个核在忙别的"，
   而是驱动单队列 + 逐包处理本身；
3. 无 TSO ⇒ 上传方向每个 MSS 一次 DMA，`tx_bytes` 才 1024 的样本里也能看到发送路径没有任何聚合；
4. 未排除：MDIO/内部 GPHY 或 MAC 侧是否有额外节流（原厂那套 `/proc/capability/*` 私有节点我们没实现）。

**没测的部分，别当成已测**：LAN↔LAN 交换（要两个口同时插线，只有 `lan1` 有 link，其余 `carrier=0`）、
WAN 侧 NAT、`nf_flow_table`/`hw-tc-offload` 是否真的把桥接流量卸载在硬件里（`ethtool` 报 `hw-tc-offload: on`，
但驱动里有没有对应实现没查）。⇒ 想验千兆真实上限需要**第二台有线机器**（已在会话里问过，未答）。
镜像里有 `iperf3`（`/usr/bin/iperf3`），测速工具在 `out/tcpblast.mjs`（按秒差分 + 活跃窗口求均值，单位已修正）。

### P.5 下一步候选修法（按"成本 / 一次开机能不能只动一个变量"排）

1. **在驱动的下载流程里逐步采样 `MT_TOP_MISC`**（把 regprobe 的读法搬进 mt7915：每次固件段 DMA 之后读一次并 `pr_info`）。
   现在能分清"等待太短 / WACPU 真没起来 / MMIO 已不应答"三种状态，但只在驱动之外、且必须避开 probe 窗口。
   一次开机就能定位停在哪个 state，是性价比最高的一刀。
2. **绑之前显式复位芯片**：DTS 里 `enable-gpios`/复位脚（`&gpio3 5` 还是 `&gpio3 7` 未定案，见本文"仍然未知"）拉低再拉高、
   等 ≥100 ms 再 bind。假设：冷 PERST 之后 MCU 需要比 U-Boot 交接后更长的稳定时间。⚠ 属于"可能致命"类，做之前确认 failsafe 可用。
3. **挖原厂的时序**：`device/backup/mt7916.ko`（5.5 MB，MTK 私有全 MAC 驱动，`mt7915_*`/`mt76_*` 符号全为 0，
   有 `chip_fw_init` 这个 `bl hc_get_ops` 派发器）里 `chip_fw_init`/`multi_hif_*` 的调用顺序可以反汇编比对；
   `device/backup/kernel1.bin` 是明文 uImage（comp=0），可看原厂内核侧 PCIe/复位路径。
   这条路不需要真机，安全。
4. **关联即死**：先解决 1（拿到稳定可用射频），再跑 `device/stages.sh` 的 S4。现在的证据只到
   "死在握手期间、`sta` 常常还没置 1、内核完全不打印、AER 三组计数全 0"，即 CPU/总线级硬死。
5. **看门狗自救这条路已堵**：原厂 DTB 的 `watchdog@00800620` 是 `arm,cortex-a9-twd-wdt`（GIC 私有定时器区），
   6.18 树里没有该 compatible 的驱动，且 TWD 的 watchdog 模式只发中断 —— IRQs-off 硬死时救不了。
   原厂用的是私有 `CONFIG_MONITOR_WATCHDOG=y`，寄存器协议要从他们内核里挖。

### P.7 复现性与打包几何（今天用"重打包同一份构建"验出来的）

搬完目录后拿 `out/gen1/` 走了一遍 `node build/host/release.mjs --dir out/gen1 --out out/consolidate-test.bin`
（`--dir` 里没有 `payload/{kernel,root}` 时脚本会自己解 sysupgrade tar；本次解出
`out/gen1/payload/sysupgrade-zte_zxhn-e2631/{kernel,root}`），顺带钉死三件事：

1. **打包是确定性的**：同一目录连打两次 → 20,972,052 B、sha256 **完全相同**
   （`a77d945950426e70e87ea9069c2584ff6778f7d4b59ed898947a4dc44a4b74c4`），两层静态验证全 PASS。
2. **包内布局的准确刻度**（今天对着字节重新核对，早先"kernel 从 0x214 起"的说法不准）：
   `0x00` 是 16 字节四个魔数（`99999999 44444444 55555555 aaaaaaaa`）⇒ `0x14` 起 512 字节 verhdr ⇒
   `0x214` 起 32 字节**槽标记**（首字 `33333333`）⇒ **uImage 从 `0x234` 起**（= verhdr `+0x38` 里那个"内核在包内偏移"）⇒
   rootfs 从「声明的内核区长度 + 0x214」起，我们把内核区声明成 4 MiB，所以 squashfs 的 `hsqs` 落在
   **`0x400214`**（全文件只出现一次）。
   ⚠ 坑在细节上：OpenWrt sysupgrade 里取出的 `kernel` 成员**自带那 32 字节槽标记**，
   所以它的头四字节是 `33333333`、它在包里落在 `0x214` 而不是 `0x234`。切包脚本按 `0x214`/`0x400214`
   切是对的（那正好是"标记+内核"和"rootfs"两个起点），按 0 / 0x400000 切会拿到 `0x99999999` 那种魔数填充。
3. **板上那一份 ≠ `out/gen1` 重打包出来的那一份**：`out/e2631-openwrt-gen1.bin`（15:59，sha256 `2406a6b9…a4cb`，
   实际经 `supgrade.html` 刷进槽 1 的就是它）与 `out/gen1`（16:37 的 collect）比：
   "kernel+槽标记"那段（`0x214` 起 3,465,718 B）**逐字节相同**，rootfs 段从 squashfs 超级块 **+0x4（inode 数）** 就开始不同
   （长度都是 7,915,520 B，差 7,686,118 字节）⇒ 同一个内核配**两次不同的 rootfs 构建**。
   ⇒ 结论很实用：**要拿"板上那一版"必须留着 `out/e2631-openwrt-gen1.bin` 这个文件本身，重打包复现不出它**；
   下次要复现，得连 collect 的时间戳一起对上（`build/wsl/build-gen1.sh` 每次会覆盖 `out/gen1`）。

### R.1 自动回原厂不是变砖，是 `e2631-trial` 按设计触发

用户报"怎么自动回原厂了"。机制核对（`overlay/.../sbin/e2631-trial`）：START=99 的服务开机跑，

### S.1 三个决定性的硬件事实

1. **一个 PCI 功能 = 两条 phy**：`/sys/class/ieee80211/phy0/device` 与 `phy1/device` **都指向
   `0000:01:00.0`**。`iw phy` 显示 `phy1 → Band 2`、`phy0 → Band 1` ⇒ **phy0 = 2.4G，phy1 = 5G**。
   不是双 HIF；我们只 bind `0x7906` 就够了。
2. **同器件的两条 phy 靠 `+N` 后缀区分**：`/usr/share/hostap/wifi-detect.uc` 的 `phy_path()` 会
   （a）砍掉 `platform/` 前缀（当路径是 `platform/.../pci...`），（b）按 phy 序号加 `+N`。
   生成器给 5G 那条写的是 `soc/f000000.pcie/pci0000:00/0000:00:00.0/0000:01:00.0+1`。
   ⇒ **不带后缀 = 第一条 phy，`+1` = 第二条**。
3. **接口命名是 `phy1-ap0`**，不是 `wlan0`（这版 master 的新命名）。

### S.6 用户侧的命令清单（真机验证过的那条路，已写进 Release v1.2 正文）


镜像默认不上射频（这是刻意的）；官方 mt76 驱动在这块板子上**客户端一关联就整机挂死**，

```sh
# 1) 加载驱动（冷启动后第一次下载固件约 1/3 成功；若卡住只能断电重来）

# 2) 生成无线配置（镜像里没有 /etc/config/wireless，netifd 第一次会生成）
wifi config
uci show wireless | grep -E 'wifi-device|wifi-iface'

# 3) 启用并使用它（生成出来的段是命名的 radio1/default_radio1，接口默认带 disabled 1）
for d in $(uci show wireless | sed -n 's/^\(wireless\.[^=]*\)=wifi-device$/\1/p'); do uci set $d.disabled=0; done
for s in $(uci show wireless | sed -n 's/^\(wireless\.[^=]*\)=wifi-iface$/\1/p'); do
    uci set $s.disabled=0; uci set $s.mode=ap; uci set $s.network=lan
    uci set $s.ssid=E2631; uci set $s.encryption=none
done
uci commit wireless
wifi down; sleep 1; wifi up; sleep 3
iw dev                     # 期望：phy1-ap0  type AP  ssid E2631  channel 36 (5180 MHz)
```

### 真机实测（这一版的口径）

- 接口在 **5 GHz**：`phy1-ap0 type AP ssid E2631 channel 36 (5180 MHz) width 80 MHz txpower 20.00 dBm`，

- 想上 2.4G：再建一个 radio，path 用**不带 `+N` 后缀**的那条，`band=2g`：

### S.8 闪存支持对比：原厂内核 vs 我们的镜像（2026-10-14）

问题来自"不同型号的 Flash 能刷吗"。判据不是 U-Boot（它的表只服务引导加载器），而是**内核的
spi-nand 表**：Linux 侧匹配靠 (厂商, 器件) 两字节 ID，不在表里就 `unknown raw ID` → 注册失败 →
rootfs 挂不上 → 起不来（回落原厂，不砖）。

方法（已脚本化：`wsl/vendor-flash-table.sh`）：原厂升级包里 `0x234` 是明文 legacy uImage
（长度取 verhdr `+0x34`），跳过 64 B 头、找到 gzip 流解压出 vmlinux，它的字符串里就带着 ZTE
自己那张表，格式是 `SPI NAND <型号> <容量> 3,3V`：

```sh
wsl -u builder bash build/wsl/vendor-flash-table.sh        # 原厂表
strings -a <我们的 vmlinux> | grep -E '^(W25N|GD5F|MT29F|…)'  # 我们表里的型号名
```

**共同覆盖**（原厂有、我们也有同名条目）：Winbond `W25N*`、GigaDevice `GD5F*`（含 1/2/4G 全族）、
Micron `MT29F*`（SPI 档）、Macronix `MX35LF*`、Toshiba `TC58CVG*`、FORESEE `F35SQA*`、XTX `XT26G0x*`、
**海扬 `HYF1GQ4UDACAE`（我们板上这颗，内核打印 "SkyHigh SPI NAND was found"）**、ESMT `F50L1G41LB/LC`、
复旦微 `FM25S01A`/`FM25S01BI3`/`FM25G01B/02B`，另有 `PN26G0xA`、`AS5F34G04SND`、`ATO25D1GA`。

**原厂有、我们没有**（这是真正的风险名单）：

| 厂商 | 型号 |
|---|---|
| Dosilicon 东芯 `DS35*` | `DS35Q1GA`/`DS35Q1GB`（128 MiB）、`DS35M1GA`（1.8 V 128 MiB）、`DS35Q2GA/GB/GBS`（256 MiB）、`DS35Q12CXXX`、`DS35X4GBXXX` |
| FORESEE 另一族 | `FS35ND01G-D1F1QWHI100`、`FS35ND01G-S1Y2QWFI100`（128 MiB）、`FS35ND02G-S2F1QWFI000`（256 MiB） |
| Zetta 泽塔 | `ZD35Q1GAIBR`（128 MiB）、`ZD35Q2GA-1B`、`25M02GVZE`（256 MiB） |
| 其它 | `UM19A1HISW`（256 MiB）、Etron `EM73C044SNB`（128 MiB，我们只有 256 MiB 的 `EM73D044VCx`） |

**只在后缀上不同、需要按 ID 才能定论的一批**：`HYF1GQ4UAACAE/UPACAE/UTACAE`、`GD5F1GQ4U/R`、
`XT26G01C`、`MT29F1G01ABAFDWB`、`F50L1G41A` —— 上游表常用家族式命名（如 `GD5F1GQ4UExxG`）按 ID 匹配，
所以这些**很可能被覆盖**，但从字符串层面看不出来，必须拿 ID 对。

**结论**：同容量（128 MiB）换供应商时，落在上表前几族（DS35/FS35ND/ZD35/UM19/EM73C044SNB）
的机器**刷不了**（认不出闪存），其余大概率能刷。几何前提不变：**2 KiB 页 / 128 KiB 块**；
块/页变了就不是加一条 `SPINAND_INFO` 能解决的事。判定现场的那一台，最快是原厂系统里
`dmesg | grep -i "SPI NAND"` 看它打印的型号。

### S.9 闪存适配：评估完成，**决定不做**（2026-10-14 深夜）

用户问"不同型号/供应商的 Flash 能不能刷"，评估结论是**要改内核而且无法在这里验证**，因此暂停：

- **判据**：Linux 侧 `spi-nand` 表按 (厂商,器件) ID 匹配；不在表里直接 `unknown raw ID` 注册失败
  → rootfs 挂不上 → 起不来（回落原厂，不砖）。U-Boot 的表帮不上内核。
- **方法已固化**：`wsl/vendor-flash-table.sh` 从原厂包里抠内核打印 ZTE 自己的表
  （`SPI NAND <型号> <容量> 3,3V`）；原厂 vmlinux 是 **raw binary**，表在 raw 偏移 `0x64ad84`、
  基址 `0xC0008000`、每条 **40 字节**（name 指针 / mfr / dev / ? / 页 / 容量MiB / 块 / 0 / f28 / f32），
  45 条已 dump 到 `out/vendor-flash-table-dump.txt`。
- **关键坑**：原厂表的 (mfr, dev) **不能直接抄**上游驱动——读 ID 方式不同，字节就不同
  （例：F35SQA001G 原厂记 `0xcd,0x71`，上游按 `OPCODE_DUMMY` 读是 `(0x71,0x71)`；东芯那几颗上游用
  **单字节 dev ID**，正好等于原厂表的 dev 字节）。更要命的是 **OOB/纠错能力必须逐颗取**：
  上游 `DS35Q1GA` 是 `MEMORG(…64…) + ECCREQ(4,512)`，而 `DS35Q1GB` 是 `MEMORG(…128…) + ECCREQ(8,512)`
  —— 两颗同为 128 MiB/128 KiB 块，照"容量+块"猜必错。
- **零发明可搬的只有 3 颗**：`DS35Q1GA`、`DS35M1GA`（补丁在 `target/linux/mediatek/patches-6.18/010-*`）、
  `DS35Q1GB`（`412-*`）。已试搬成我们的 `032/033`，**在 6.18 树上干净应用成功**（构建日志有
  `Applying … 032/033`），随后按用户决定**撤回**（工作树已干净，v1.2 未变）。
- **其余同容量料号无上游来源**：`DS35Q2GA/GB/GBS`、`FS35ND01G-×2`/`FS35ND02G`、`EM73C044SNB`、
  `ZD35Q1GAIBR`/`ZD35Q2GA-1B`、`UM19A1HISW` —— 前几颗可以照同族模板加，但缺 OOB/ECC 参数；
  Zetta/UM19 还要新建厂商文件并先定读 ID 方案（它们的 dev 字节与东芯/FORESEE 撞车）。要补齐需
  datasheet 或一台装该 Flash 的实机，且**本机无法验证**。
- **决定**：不做。将来若有人拿着换闪存的 E2631 来问，先让他跑 `dmesg | grep "SPI NAND"` 报型号，
  照 `out/vendor-flash-parts.txt` × `out/our-kernel-candidates.txt` 的对比即可判断"认/不认"。

### U.1 事实：原厂 telnet 口令仍在公开仓库里，9 个文件


具体泄露了什么（逐文件核过内容，`out/what-leaked.sh` / `out/exposure-blobs3.sh`）：

| 面 | 内容 |
|---|---|
