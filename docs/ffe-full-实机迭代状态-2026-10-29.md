### 1. 下行硬件加速路径 —— 已实证
```
idm rx_frames=29792  rx_unicast=26101  rx_dropped=0  rx_novap=0
idm rx_submit=31840 = 2048(初投) + 29792(重投)    ← 零泄漏
```

含义：`PPE 分类器 → IDM RX 环(0x921C8000) → 拷出 → dev_queue_xmit(VAP)`

这一条是 0.2/0.3 三次失败的"下行黑洞"的最终闭环。

HE160 由 `e2631-wifi-ap` 的 band profile 写入（2.4G HE40+noscan / 5G HE160）。
用户确认设备支持 160M，此前写死 80MHz 是配置缺失，非硬件限制。

## 三、本轮修复的根因清单（按发现顺序）

1. **野指针卡死**（0.2 首刷重启循环）：`zx_eth_setup_tc` 对 mac80211 转投的
   wlan netdev 取 `netdev_priv(dev)->adapter`，那是 mac80211 私有区 →
   流表绑定经野指针加锁 → 静默卡死 → 看门狗复位。
   修：非本驱动 netdev 走 `zx_idm_adapter()` 单例。
2. **IDM 寄存器序列不完整**（0.3）：对照 plat-zxylzb_9128S.ko 注解反汇编
   `tm_pon_npp_init`/`pon_npp_idm_init` 逐条转写：
   - **IDM+0x04=TX 基址 / +0x08=RX 基址**（旧代码把 0x04 当第二 RX 环）
   - **RX 缓冲必须逐个经 IDM+0x48 投递口提交**（引擎内部环；只写共享
     描述符不投递 = 下行黑洞）
   - 补全 NPP_MASK0/1、INTEN、CFG40、PPB、IDM CFG00/10/18/1C/24、
     DEPTH=0x04000800、PP+0x20040=1600
3. **交付 skb 从未拷入帧数据**（0.3 中期）：`__alloc_skb` 的空 skb 直接
   `dev_queue_xmit` → 平板收到垃圾内存 → 网络栈被打死（ICMP 活/TCP 死）。
   修：槽位永久绑定相干缓冲，完成帧 `napi_alloc_skb + skb_put_data` 拷出。
4. **FFE 接缝指针永不赋值**：`zx_ffe_ops_register` 只写 `zx_ffe_ops`，
   而 `zx_ffe_active()` 读 `zx_ffe_ops_ptr` → FFE 控制面从未生效。
   修：注册时 `WRITE_ONCE(zx_ffe_ops_ptr, ops)`。
5. **br_fdb_find_port 无 RTNL**：6.18 断言，dmesg 实抓 WARNING。修：rtnl_lock。
6. **036 钩子入口条件错误**：`state->in->ieee80211_ptr` 对桥接客户端
   （帧从 br-lan 进栈）恒为 NULL → 上行注入永不触发。
   修：`zx_idm_hook_wlan_ingress()`（VAP 或桥主设备）+ FDB 源 MAC 反查通道。

## 四、工程侧根治（避免重复踩）

- **版本号自动化**：`scripts/build.sh` 构建前把 `E2631_VERSION` stamp 进
  rootfs 并 clean base-files，收集后强校验门禁。此前三次构建靠手工补。
- **overlay 同步陷阱（三轮教训）**：WSL 读 `/mnt/d` 有陈旧缓存，
  且 Windows 侧 Git Bash 的相对路径脚本可能写到 `D:\AI\Qoder\E2631-OpenWRT\overlay`
  （仓库外的幽灵目录）。可靠做法：
  `tar -C build -cf - overlay | wsl tar -C ~/openwrt -xf - --strip-components=1`
  并且**构建后必须验证产物**：`strings $K/vmlinux | grep "idm rx_ch="`。
- **heredoc 吞反斜杠**：`\\n` 在 Git Bash 嵌套 heredoc 会变成真换行，
  破坏 C 字符串。多行补丁一律用 Write 工具落盘 .py 再执行。

## 七、0.5：无线硬件加速真正生效（2026-10-29 12:45）

### 最后一个根因
桥接无线客户端的流量**从 `br-lan` 进入协议栈**，而 `zx_idm_wifi_ingress()`
只比较 VAP 的 ifindex（phy0-ap0/phy1-ap0）→ **每一条无线流在分类器入口
的第一个检查点就被拒绝**。这就是"5G 协商 1441 Mbps 却只有百兆"的全部原因。

修复：入口判定接受桥主设备（RCU 安全的 `netdev_master_upper_dev_get_rcu`）。

### 实机前后对比（192.168.5.28）
| 指标 | 修复前 | 修复后 |
|---|---|---|
| `ppe_flows` | 2 | **24-26** |
| `ppe_add_skip` | 549 | **0** |
| `HW_OFFLOAD` 流 | 0 | **13** |
| `ppe_skip[]` 15 类 | — | **全部 0** |
| CPU | 忙 | **100% idle** |
| IDM 下行交付 | 停滞 | 持续增长 |

### 残留（预期行为）
- `wifi_egress_skip[nofdb=34]`：目的 MAC 暂不在桥 FDB 的流回落软件路径
  （新客户端/ARP 未学时正常）。
- 上行注入 `inject_ok=0` 是**正确的**：上行帧已在 CPU（mt76 不共享 IDM
  缓冲），只有下行能走硬件；这是本架构的最优形态。
- 已卸载流的 conntrack 包计数停止增长也是正常的（硬件直转不过 conntrack）。

### 新增诊断（长期资产）
`dma_state` 现在输出 15 类流拒绝原因 + 4 类 wifi 出口失败原因，定位此类
问题不再靠猜。
