# zwzzrl 上游采纳与 IPv6 硬件路径结论修正（2026-10-30）

> 来源：`zwzzrl/zte-e2631-openwrt` origin/main `008eeaf`（2026-10-29，九轮真机取证）。
> 该仓库与 npu 分支方向互补：**zwzzrl 保留主线数据面、只把表格数值换成原厂的**；
> npu 连控制面一起按原厂 FFE/NPU 语义重写。他们的九轮真机取证（我们受禁刷约束
> 做不了）直接补 npu 的证据缺口。本文记录已核实结论与已采纳内容。

## 1. zwzzrl 路线定性（其 architecture.md 自述）

- 代码自写（"programmed from scratch, with the values of the vendor firmware"），
  非反编译搬运；数值取原厂：CLA rule 寄存器 152/153 逐字、CRC32 双多项式
  （0x04c11db7 / 0x1edc6f41）取自 vendor `.rodata`、extract index 9/10 +
  rule 0x98/0x99 取自 tm.ko 参数编排，每项写寄存器读回验证。
- 控制面用主线 netfilter flowtable / TC_SETUP_FT（新写，对 Linux 6.18 TC API）。
- **原厂不用主线这套**：vendor vmlinux 里 `nf_flow_table` / `flow_cls_offload` /
  `TC_SETUP_FT` 各 0 次。原厂自研加速 = switch.ko `npu_drv_*` + tm.ko PP/分类器
  + xdpi.ko。
- 双向吸收：他们吸收了我方 v1.8.0 三条修复、wanport 保护、WiFi HE40/HE80
  （a6e75bf）。

## 2. IPv6 硬件路径结论（修正我方 ffe 线 f50b85b 的记录）

1. **0x388000 的 48 字节表 = IPv6 组播（MLD）表，不是单播转发表**（a36f0df，
   真机写读回验证）。我方 ffe-full 曾把这张表记成"原厂 IPv6 硬件表"，错误。
2. **CLA 的 v6 哈希查找被排除**（e3d53e8）：单窗口规则也 617/600 对 98/600，
   不是 key 格式问题——这颗芯片的分类器没有 v6 哈希查找。
3. **原厂把 IPv6 当一等卸载类型，快路径在 NPU**（a11979b）：
   - switch.ko：`npu_ipv6_l3tcp{up,down}_cap` 一整组按类计数器；
   - tm.ko：`cla_set_local_ipv6_addr` 写 ONU reg 19（0xe3028，4×32 bit =
     一个本地 IPv6 地址）、reg 23（0xe303f，8×32 bit = ONU S/D IPv6）；
   - IPv6 SNAT/DNAT RAM 长度、NPTv6 与 DSLite 字段、IPv6 MLD 表；
   - 原厂代码里**没有 0x86dd 常量**——它不靠 IPv6 ethertype 陷阱收帧。
4. **trap-DMAC 机制与 IPv6 TCP 全断的根因**（a11979b，真机复现）：
   `ppe_active=1` 会把路由器 MAC 从 trap-DMAC 表挪进 ONU「routed」表并清空
   trap-DMAC；IPv6 ethertype 陷阱在 `sw_members != 0` 时本来就关（三个 LAN 口
   在 br-lan 恒成立）→ IPv6 帧失去唯一进 CPU 的通道 → SYN 能过、载荷和应答
   全丢。`hw=0` 把 MAC 放回 trap-DMAC 表即恢复。
5. **容量上限**（008eeaf）：127 条流（7 位改写索引、index 0 保留、原厂最多用
   125）、≈60 条双向连接、溢出 -ENOSPC 回软件路径（ppe_add_fail/ppe_add_skip
   之别）；384 是哈希槽数不是流容量。

## 3. 已采纳进 zxnpu-ppe.c（本提交）

- **PP 窗口 0x40000 → 0x400000**：vendor 映射整 4 MiB；SBRG 在 +0x388000，
  旧映射看不到，且越窗访问会直接 oops（zwzzrl 踩过：选择子地址重复加 base
  → 0x710184 → 越窗）。窗口尺寸按原厂钉死。
- **SBRG 访问套件**（`sbrg` 命令族，全部标注来源）：
  - `zxnpu_sbrg_hash`：34 字节 key（sip[16]+dip[16]+vlan u16le）**倒序**喂
    CRC-16/CCITT（init 0），&0x3ff——200/200 随机 key 与 vendor 一致（t_hash.py）；
  - `zxnpu_sbrg_slot`：vendor reg 29（PP+0x388184，mask 3）选槽：
    sel==1 → `((hash&0x7f)<<2)|0x200`，否则 `((hash<<2)&0xff)|0x300`；
  - `zxnpu_sbrg_entry`：384 位小端位流——bit0..2 valid/age/mode、3..14 vlan、
    15..78 dip[8..15]、96..103 端口掩码、104..167 dip[0..7]、192..255 sip[8..15]、
    288..351 sip[0..7]；word 8/11 恒 0（60/60 随机记录复验）；
  - `zxnpu_sbrg_xfer`：读=start 位 1，写=word 0 最后（锁存字）；vendor 写序
    =先读 4 张 table × 4 块、再只写 table 0；
  - 真机判据（zwzzrl v9c slot1）：`h` 输出与厂商代码逐字相同（hash 0x3fd、
    sel 1、槽 0x3f4），写读回逐字一致，删除后读回全 0、LAN 转发不受影响。
- 门禁纪律不变：`sbrg h` 纯计算+一次寄存器读，免 enable；`sbrg a|d|read`
  全部在 `zxnpu_ppe.enable=1` 之后。

## 4. 对 npu 设计的影响

1. **FFE v6 维持 CPU 快路径**：zwzzrl 九轮真机证据独立支持我方 ffe-full 的
   定性（v6 硬件表行不可得 → CPU 承接）。v6 单播卸载的正确路径是 NPU
   （`npu_drv_*`/xdpi.ko 语义），其逆向仍属 P3 范围。
2. **zxnpu-ppe 重写铁律：永不摘 IPv6 trap 那一半**。学 zwzzrl 根因：
   `zx_update_traps` 类逻辑写 trap 时必须保留 `ETH_P_IPV6` 半边，无论
   ppe_active 与否——否则复刻他们踩过的 IPv6 TCP 全断。
3. **流容量建模**：FFE 控制面按 127 条流/384 哈希槽设计，溢出 -ENOSPC
   回软件路径并计数（ppe_add_fail / ppe_add_skip 分开统计）。
4. **boot 安全模式**：zwzzrl 的 PPE 引擎用 late load（START=99）+ pending
   guard（带 boot 身份防一次性任务重生）。npu 驱动已按更保守的
   enable=0 默认设计，与该模式等价且更严。

## 5. 打包防裸 zImage 门（cf58a25）——复核完成，我方已覆盖

zwzzrl v9/v10 曾把无法引导的裸 zImage 发出去，后加"kernel extent 不可引导
即拒绝打包"的门。复核我方 `host/verify_pkg.mjs`：裸 zImage 场景会硬失败——
`kernel extent begins with a legacy uImage magic`（0x27051956）、
`uImage os/arch/type/comp`、`load == entry == 0x40008000`、`ih_dcrc 自校验`
全是 `ok` 级硬门；zImage 特征（首字 0xe1a00000）另有 warn 提示。无需补。

## 6. 后续交叉验证点

- zwzzrl 的 `sbrg_hash` 与我方 doc 12 的 CLA 45B key 哈希是**两张不同的表**
  （SBRG 组播表 vs CLA ACL 表），别混用。
- 其 `vendor-emu` 工具链（t_v6entry/t_v6slot/t_hash）可在离线复算我方
  zxnpu-ppe 的实现正确性，不依赖真机。
- 原厂 ONU reg 19/23 的 IPv6 地址寄存器堆是 P3（FFE v6/NPU 路径）的新证据入口。
