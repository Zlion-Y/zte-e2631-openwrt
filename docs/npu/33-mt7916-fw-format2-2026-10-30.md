# 33 — MT7916 固件 format-2 分段表与下载配方（2026-10-30）

本篇把 G3.3 最后一块静态空白补上：vendor `mt7916.ko` 的
`parse_fw_v3` / `load_fw_v1` 到底怎么读 `WIFI_RAM_CODE_MT7916.bin`，
以及 ROM patch、WM、WA 三个镜像各自的下载命令。全部结论来自
`mt7916.ko` 反汇编 + 对现网镜像的逐字节解析，**未刷机**。

## 1. 选择哪个解析器

`mt_fwdl_hook_init`（`0x1D6FBC`）按 chip_cap 的字选择回调：

| cap 偏移 | 含义 | 取值 → 回调 |
|---|---|---|
| `0x114` | patch 加载器 | 0 → `load_patch_v1` |
| `0x11C` | patch 解析器 | 0 → `parse_patch_v1`，1 → `parse_patch_v2` |
| `0x118` | fw 加载器 | 0 → `load_fw_v1`，1 → `load_fw_v2_compressimg` |
| `0x120` | fw 解析器 | 0/1/2 → `parse_fw_v1/v2/v3` |

现网镜像不是压缩流（9 段 payload 合计与文件体积只差 128 B 对齐/补齐），
且 `n_region=9` 超出 v2 的两 band 模型，所以 MT7916 实际是
**`parse_fw_v3` + `load_fw_v1`**。

## 2. 镜像布局（已用三个真实文件验证）

```
[payload 0][payload 1] ... [payload n-1] [padding]
[40 B 描述符 x n_region][36 B trailer]
```

描述符（`parse_fw_v3` 从 trailer 往回走 `n*40`，与 mt76
`struct mt76_connac2_fw_region` 逐字段一致）：

| 偏移 | 字段 | v3 行为 |
|---|---|---|
| +0x00 | decomp_crc | 不解压时忽略（本镜像全 0） |
| +0x04 | decomp_len | 忽略 |
| +0x08 | decomp_blk_sz | 忽略 |
| +0x0C | rsv[4] | 跳过 |
| +0x10 | addr | 下载地址 |
| +0x14 | len | 段长；payload 依次紧排 |
| +0x18 | feature_set | 见 §3 |
| +0x19 | type | 忽略 |

trailer（36 B）：`chip_id, eco, n_region, format_ver, format_flag,
rsv[2], fw_ver[10], build_date[15], crc@+0x20`。v3 要求
`format_ver == 2` 且 `format_flag & 1`。

### 2.3 ROM patch `mt7916_patch_e1_hdr.bin`

sha256 `6524f8bc…`（8,672 B）。`parse_patch_v1`（`0x1D5770`）只剥掉
**30 字节头**（build_date[16] + platform[4] + hw_sw_ver + patch_ver +
vendor），其余 8,642 B 整段下载到 `chip_cap[0x12C] = 0x04000000`，
因此 0x11223344 魔数属于下发给 MCU 的内容，不是要跳过的头：

```
PatchSemGet  type 0x10 cmd 0x17 {op=1}
AddressLen   type 0x05 cmd 0x17 {0x04000000, 8642, 0x80000000}
FwScatter    type 0xEE cmd 0x10 {chunk}
PatchFinish  type 0x07 cmd 0x17 {0,4 字节}
```

## 3. feature_set → AddressLen mode / FwStart option

`load_fw_v1`（`0x1D5A48`）逐段：

```
mode = 0x80000000 | (fs & 7) | (fs & 1 ? 0x08 : 0) | (fs & 0x10 ? 0x40 : 0)
       | (band == 1 ? 0x10 : 0)
```

与上游 mt76 `mt76_connac_mcu_gen_dl_mode` 对照：

| fs 位 | 语义 | 落到 mode |
|---|---|---|
| 0 | encrypt | bit0 + bit3（reset sec IV） |
| 1..2 | key idx | bit1..2 |
| 4 | encr mode | bit6 |
| 5 | override addr | 不置位，只记 override |
| 6 | non-DL | vendor 未用；驱动按上游跳过并且不推进 offset |

`FwStart{option, override}`：bit0 = 有 override，bit2 = WA（band 1）。
散块大小 = `4096 - chip_cap[0x134]`；驱动沿用保守的 512 B。

## 4. 驱动与工具改动

- `host/fw-plan.mjs`：离线解析 WM/WA/patch 并打印计划；
- `zxnpu-wlan.c`：新增 `fw-plan wm|wa`、`fw-dl wm|wa`（解析 + 逐段
  AddressLen/FwScatter + FwStart），`mcu-dl` 的 patch 偏移从 0x40 改为
  30、Finish 负载补齐 4 字节；
- 修掉分发顺序 bug：`fw` 前缀此前会吞掉 `fw-info` / `fw-start`；
- `e2631-wlan-probe --commit` 现在按 patch -> WM -> WA 顺序执行；
- 新增 FWDL 环：`GetRealPortQueueID`（0x1C112C）对 type 0xEE 返回
  chip_cap[0x162]（FWDL qid16，0x18024400），其余命令走 0x8000
  控制队列（MCU_WM qid17，0x18024410）。因此 scatter 走环 0，
  AddressLen/FwStart/Sem/Finish 走环 1；`fw-state` 读 L1 窗口看
  1（下载态）/3/7（就绪）。

## 5. 边界

- 仍未刷机；`PatchSemGet` 的响应状态、FwStart 的 ack、MCU 事件同步
  都还没有真机验证。
- 下载只覆盖 MCU 固件链路；WFDMA 队列初始化、MCU 事件解析、AP 数据面
  属于后续阶段。

## 6. FW 状态握手（`ctrl_fw_state_v2` / `AsicGetFwSyncValue`）

`ctrl_fw_state_v2`（0x1D5198）先读 `AsicGetFwSyncValue`，再按入参选择
目标值：

| state | 期望 | 超时动作 |
|---|---|---|
| 0（进入下载态） | sync ≤ 1 | 发 `MtCmdRestartDLReq` 再等 ≤1501 ms |
| 1/2 | sync == 1 | 否则重启下载 |
| 3（启动完成） | sync == 3；chip_cap[0x110] & 2 时为 7 | 轮询 1501 ms |

`AsicGetFwSyncValue` 经 arch_ops[0xFC] 读 `MT_TOP_MISC = 0x180600F0`，
走 L1 窗口：

```
写 0xFE260 = 0x1806          (MT_HIF_REMAP_L1_MT7916)
读 0xE0000 + 0xF0  & 7       (MT_TOP_MISC_FW_STATE)
```

取值与 mt76 `FW_STATE_*` 一致：1 = firmware download，3 = normal
operation，7 = ready（含 WA）。驱动新增 `fw-state` 命令（commit=1 时
真正写 remap 窗口），`fw-dl` 在 FwStart 后轮询到 3/7 并打印。
