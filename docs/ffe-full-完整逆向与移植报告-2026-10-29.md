## 0. 一页结论

1. 原厂有线+无线加速 = 同一套 cspkernel4.1 内建 **FFE（流学习控制面）+ NPU
   （PPE 分类器硬件卸载）**，tm.ko 是引擎寄存器 SDK，switch.ko 是有线挂入点，
   mt7916.ko（MTK 私有栈）通过 `idm_skb_stack_{push,pop}` + IDM 环挂入。
2. **实机只读观测实证**（§3）：FFE v3.6.6 运行中，IPv4 TCP/UDP 流全部
   `npu:1`（NPU 硬件卸载），WiFi 流（wlan0↔pon）同表学习、`passed dev:
   [wlan0]->[nbif0]->[eth0]`——**无线流与有线流走同一张 NPU 流表**。
3. **IPv6 硬件路径本轮闭合到"可直接照抄"的程度**（§5）：FFE 层 IPv6 协议
   层键长 44B、tcp/udp 槽表 1024 条；tm.ko 的 L3 会话快路径 v6 分支把流键
   降维打包进与 v4 相同的 7 半字槽（saddr[2:8]+saddr[12:16]+daddr[0:4]）；
   nat6 NPU 插件匹配器提取双向 16B 地址+端口+TOS 共 32B。**但 v6 的 CLA
   提取规则表（EXTRA_INDEX/RULE 的 IPv6 行）无法在不写设备的状态下读出
   （tm sysfs 在 E2631 上是空桩、/dev/tm_sample_dev 实为 PON PRBS 测试
   接口，§3.4），本分支按既定风险政策把 v6 保持 CPU 快路径**（§6.4）。
4. 移植产物（ffe-full 分支，本地提交，不推远端）：ffe.c（FFE 控制面，已
   在 main）+ **恢复 T1.5 无线加速**（zx279128s-idm.c 环形引擎 + ppe.c
   12bit egress/VAP 放行 + mac80211 991 shim + nf_flow_table_ip 036 钩子
   + hotplug flowtable 重载）+ apply.sh 断言与 FFE 默认开。构建/离线验证
   见 §8。

## 2. 驱动结构与初始化流程（综合各逆向笔记，本轮校对）

### 2.1 硬件地址空间（vendor enc=(phys-0x92000000)>>2，三重交叉验证）

| 块 | 物理 | 职责 |
|---|---|---|
| PP | 0x92380000 | CLA 分类器(流表 hash0/1)、PM 包修改、SBRG 交换 MAC/VLAN 表、ADM 警务 |
| TM | 0x92340000 | QMG 队列、SCH 调度、RED、**BMU 缓冲池**(+0x8000)、PON DMA |
| NPP | 0x921C0000 | GREG/SDET/SIPC/SPA/UOPC/SOPC、**IDM(+0x8000)** |
| SMAC | 0x92200000+n*0x10000 | 5 个 GE MAC |

**IDM（0x921C8000）= WiFi↔fabric 的注入/递送引擎**：RX ring A/B 各
2048×8B 描述符（基址 IDM+0x04/+0x08）、TX 1024×8B（软件管理）、kick=
IDM+0x44 写 count<<16、完成=+0x4C 读清低 16 位；RX 描述符
w1[13:0]=len、b6[2:0]=源通道、b7[7]=idm0/idm1；TX 描述符 w0=总线地址
（phys+0x40000000 别名）、w1=len[13:0]|port<<28|valid<<31。

### 2.2 初始化顺序

```
plat ko init_module:  校验 BMU 保留内存 → iomap 5 个 DT 节点(pon/npp/tm/pp/idm)
  → pon_npp_idm_init(idm0/idm1 netdev + ring + 512 skb 预填 + idm_skb_stack)
  → pon_npp_spa/sipc/smct/smac/uopc_init → pon_tm_bmu/dma/queue/net/int_init
  → hwnat_set_hook_ptr → request_threaded_irq(npp)
tm.ko init_module:    chardev("tm_sample_dev",198) + sysfs → tm_initial:
  smac×5(get/set cfg) → tm_pon_tm_initial(reg/red/qmg/sch)
  → tm_pon_pp_initial(reg/sadm/brg/cla/adm/dpa/pm)   ← CLA 上电在此
  → tm_pon_npp_initial(greg/sdet/sipc/uopc/sopc/spa/pm)
switch.ko:            sw_public_* 注册 + npu_hff_register（FFE NPU 驱动挂点）
mt7916.ko:            qm_init（私有 QM）+ idm_skb_stack 领用 RX 缓冲 + pp_mbss
                      （Andes 命令开固件侧 PP 卸载）
```

关键事实：**WiFi 伪端口 0x18-0x1F 无需任何上电寄存器**——它是 CLA w0[23:12]
egress 值的硬布线译码（bit4=走 IDM、bit3=idm 选择、[2:0]=通道），NPP GREG
只使能 7 个逻辑口（清 authen/closed）+ SIPC rx_en。`wlan_to_idm_map`
（内核静态表）：wlan0-3→(idm1,0-3)/0x18-0x1B；wlan5g0-3→(idm1,4-7)/
0x1C-0x1F；apcli0/5g0→(idm0,1/2)/0x11/0x12。

### 2.3 数据面：有线

```
首包（CPU 学习）: gmac RX → ffe_learn_skb → ffe_flow_key(16B 基键+协议层)
  → 128B 槽表 → ffe_npu_filter_flow 过滤 → npu 驱动 ops
  → switch.ko sw_acl_l3_hardfast_session_add → tm zte_api_fast_l3_session_add
  → tm_acl_get_fastHashRule（w0[23:12] egress + 45B 键 CRC16 双 bank）
  → CLA hash0(256)/hash1(128) + PM 重写索引
后续包: NPU 直转（CLAS 命中 → PM 重写 MAC/IP/端口/TTL → egress 端口），
  例外/未命中 → ffe_receive_skb/fkb 回栈（backlog）。
状态联动: conntrack 删除 → ffe_flush_flow_by_conntrack；组播 → maddr4/6 flush。
```

### 2.4 数据面：无线（实机实证 + 调用图重建）

```
下行 WAN→WiFi: WAN gmac RX → CLA 命中（egress=0x18-0x1F）→ 硬件译码进
  IDM RX ring（2048×8B）→ idm1 NAPI（IRQ CPU1，实机 411 万次）→ idm_net_poll
  → mt_rx_pkt_process 直接无线发送（write_tmac_info_offload_pkt，全程不过
  netif_rx/mac80211）
上行 WiFi→WAN: mt7916 RX（缓冲=idm_skb_stack_pop，本就在 PP 可见内存）
  → IDM TX ring 注入 fabric（ingress=VAP 通道）→ CLA 命中（流双向同键）
  → PM 重写(SNAT) → egress=WAN 物理口
慢路径: gmac → wb_recv_skb（按 VAP MAC+VID）→ __nbif_recv_skb（剥 802.1Q
  路由元数据 tag）→ netif_receive_skb(nbifX) → br0
```

实机佐证（§3）：`idm1: RX 6.15MB/5023 包` 承载真实 WiFi 流量、idm0=0
（本机无 apcli 流量）；nbif0 计数与 wlan0/5g0 相互印证。

### 3.3 死接口定性（重要排障结论）

- `/proc/zte/sys/ffe/{hash,learnlist,npu,scripts,sharedata}` 与
  `/proc/idm`、`/proc/idm_fdb`：**cat 为空**——这些文件的 dump 由 cmd
  写入触发，只读约束下不取。
- **tm sysfs（/sys/devices/platform/tm/ppCla|ppBrg|nppSpa|…）全部为空**：
  E2631 tm.ko 的 `tm_devRead/tm_devWrite` 是 `return 0` 空桩（本地反汇编
  实证；F670L 的 ghashtable/ghashram 调试面在 E2631 上不存在）。
- **/proc/tm/shell 是内核调试器**（shellproc.ko：按符号调用任意内核函数、
  读写符号、栈回溯）——只读约束下不使用，且与引擎表 dump 无关。
- **/dev/tm_sample_dev(198:0) 实为 PON PRBS 测试接口**（tm_devIoctl：
  0x6040=ztePonCfgPrbsRxBist、0x6041=ztePonGetPrbsCounters，本地反汇编
  实证）——不是通用寄存器通道。

### 3.4 由死接口推定的边界

CLA 流表/提取规则表的运行期内容在本机不可只读获取 ⇒ **无法用实机 dump
直接抄出 IPv6 提取规则行**。IPv6 键格式改由静态逆向闭合（§5），并按
§6.4 的风险政策决定不把 v6 放进硬件表。

## 5. IPv6 硬件路径逆向（本轮新成果）

### 5.1 FFE 层（vendor kernel vmlinux，kallsyms 重建）

- `init_ipv6_packet_layer`（c0607170）：注册 IPv6 包层，**键长 44B**
  （32B 地址 + 端口/协议等）；`init_ipv6_tcp_proto/udp_proto` 槽表
  **1024 条**，raw/mc 各 16 条（对照实机 ipv4_tcp slot_size:4096）。
- `ffe_ipv6_hash`（c041a274）：4 字（16B）Jenkins 式混合——对 v6 多播
  流哈希目的地址 16B；`ipv6_multicast_insert_flow` 用两个 memcmp(16)
  比较 key+8/+24 两个 16B 区域 = **源地址、目的地址**。
- NPU 插件框架：`npu_register_driver`（7 槽驱动链，npu_main_init）；
  能力插件 `npu_cap_{nat6,pps,mc}`，`npu_cap_setup` 把驱动的
  front/backend ops 挂链并建 proc。
- **`npu_cap_nat6_front_create`（c041be8c）完整还原**：门控 =
  flow->flags & 0x700（nat6 位组）；提取两方向 path_info 的键内
  +8（16B 源地址）与 +24（16B 目的地址）、协议、端口（TCP/UDP）、
  TOS（键描述符字节 0/1 各取半字节拼合）→ 32B 结果结构；两方向
  地址不一致（跨前缀翻译）即命中并清 flow flag bit0 返回 1。

### 5.2 tm.ko 层（L3 会话快路径，E2631 tm.ko 本地反汇编）

- `tm_acl_fast_add_v4v6(v4_en, v6_en, match, rule)`：**match[0x0C]
  类型字段 ==3 为 IPv6、==4 为 IPv4**（type-3/type-4 判零后写入
  is_v6/is_v4 全局）。
- `tm_acl_get_fastHashRule` v6 分支（0x490ac，r0=v6 标志分流）：
  从 match+0x60 的地址区取 saddr6[16B]+daddr6 前 8B，**降维打包进与
  v4 相同的 7 半字槽（rule[0x13..0x1f]）**：
  `hw = [saddr[2:4], saddr[4:6], saddr[6:8], saddr[12:14], saddr[14:16],
  daddr[0:2], daddr[2:4]]`——哈希键是**抽样键**（10B 源 + 4B 目的），
  精确匹配由 CLA match RAM（完整五元组）承担；w0 组装与 v4 同函数
  （egress 12bit 写 w0[23:12]，WiFi 0x18-0x1F 位 16=1）。
- v4 的提取规则常量（`zx_ppe_v4_index/v4_rule`，索引行 9/规则行
  0x98）**不出现在 tm.ko**——它们由 FFE/switch 侧编程；v6 行号与
  内容在 E2631 上无只读通道（§3.4），这是 v6 硬件表未在本分支启用
  的直接原因。

### 5.3 结论

原厂对 IPv6 的硬件卸载 = FFE v6 协议层（1024 槽）+ nat6/前缀类插件 +
tm 快路径抽样键 + match RAM 精确比对。**移植所需但不可得的唯一一块 =
v6 CLA 提取规则行内容**；拼凑猜测会让"看似建表、实际丢包"（抽取偏移
错一字节即静默黑洞），故本分支 v6 走 CPU（见 §6.4），硬件 v6 留待
GPL 源码索取（泄露路径自称 `/zte/csp/opensource/`）或只读寄存器通道
后的下一轮。

（mac80211 下 CPU 一跳）；上行 `mt76 RX→nf_flow_table 钩子→IDM TX 注入
（ingress=VAP 通道）→CLA 命中→PM 重写→WAN`。

### 6.2 有线加速（FFE 控制面，已在 main、本分支默认启用）

ffe.c 不变：rhashtable 流表（v4+v6 键）、学习→PPE 导出原语、conntrack/
fw4 生命周期随 flow_offload 回调、`/proc/zx-ffe/cmd`（on/off/flush+统计
+idm 栈深度）。本分支 apply.sh 默认 `CONFIG_ZX_FFE=y`（E2631_FFE=0 可关）。

### 6.3 配置接口对齐

| 原厂 | 本移植 |
|---|---|
| `/proc/zte/sys/ffe/cmd` 八协议 0/1/2 | `/proc/zx-ffe/cmd` on/off/flush + 统计（协议级开关=软流表 + PPE 层各自的 -EOPNOTSUPP 决策，v4 硬卸载、v6 CPU） |
| ffe 自管 rps_cpu_map=0 | 保持 main 的 e2631-netune（rps 粘性） |
| idm_skb_stack（4 栈） | ffe.c 导出同形原语（vendor API parity，mt76/mac80211 不需要）+ idm.c 真实环形引擎 |

### 6.4 IPv6 完整支持的边界（如实声明）

- **网络层 IPv6 完整可用**：trap 修复（v1.4 f6effe3）保证 PPE 激活时
  IPv6 恒走 CPU；软流表（NF_FLOW_TABLE_INET）承载 v6 快转；桥接
  LAN↔LAN v6 不受影响。fw4 默认 flowtable 含 v6。
- **FFE 控制面**学习并统计 v6 流（键含 v6 地址），但**不写入硬件表**
  （`-EOPNOTSUPP` → fw4 软流表持有），理由=§5.3（提取规则行不可得 +
  静默黑洞风险 + 本轮离线约束）。原厂语义中 v6 的 "1=FFE 软快转" 档
  与此对齐。
- 硬件 v6 升级路径已铺好：ppe.c 的键/表构造是纯函数（`zx_ppe_halfwords/
  zx_ppe_slots/zx_ppe_hash_entry`），取得 v6 提取规则行后加一组
  `zx_ppe_v6_index/v6_rule` + v6 halfword 打包即可，ffe.c 的 v6 分支
  从 `-EOPNOTSUPP` 翻成调用点。

### 6.5 apply.sh / 门禁

- FFE 默认 ON（ffe-full 分支语义），marker 改 `ffe-full branch`，awk
  同时清除两种历史残留行。
- 新增断言：IDM 四件（idm.c/035/036/991）存在、hotplug 存在、
  eth.h (+25/−6)、main.c (+12/−2)、ppe.c (+120/−40) 差异上界——

## 7. 风险与回退

1. **无线硬件路径首次上电**：IDM kick/done 语义、`w0[23:12]` 完整端口
   值（0x18-0x1F vs 低 nibble）两项按逆向实现，留 `wifi_egress_low`
   模块参数一键切换；离线无法闭环，首刷观测点=idm 计数（`/proc/net/dev`
   的 idm0/idm1）、ppe_flows 增长、WiFi 客户端吞吐对比 200M 基线。
2. **FFE 学习路径**：ffe-0.1 起未上过实机；本分支把它与无线叠加，
   首刷建议先 `echo off > /proc/zx-ffe/cmd` 对照（软流表兜底始终在）。
3. 全部改动可用 `E2631_FFE=0` + 模块参数 `wifi_offload=0` 双开关
   逐层降级到 v1.8.0 已验证行为；hardware 兜底（trap 表）不受影响。
4. 不推远端：本分支仅本地提交（任务约束）。
