E2631 槽结构定案 —— "两个内核槽 + 一个共享 rootfs" 是错的
================================================================
日期：2026-10-12
证据级别：A（真机直读 + 整片 dump + 官方包，三方互证）

────────────────────────────────────────────
【0】一句话结论
────────────────────────────────────────────
E2631 是**整机 A/B 双槽**：槽 A 在 0x700000、槽 B 在 0x2300000，各 28 MiB（0x1C00000）。
**每个槽各带一份完整内核 + 一份 rootfs。rootfs 不是共享的 —— 是各槽各一份拷贝**，
出厂时两槽内容逐块相同，只差 1 个 128KB 的版本头块。

两槽内核的**加载地址/入口地址完全相同 = 0x40008000**；不同的只有 **flash 存储偏移**。

⇒ 用户质疑成立。我上一轮"E2631 只有两个内核槽 + 一个共享 rootfs，不完全同构"的说法**作废**。
   E2631 与 SR1010 在槽制上其实**是同构的**（都是整机 A/B 双槽）。

【2】两层结构，不要混着说
────────────────────────────────────────────
层 1（整机）：
    槽 A [0x700000, 0x2300000) 28 MiB
    槽 B [0x2300000, 0x3F00000) 28 MiB
    每槽 = 槽头 + 内核 + rootfs（+ 插件区），即**一整套系统**。

层 2（槽内组件 —— 即 /proc/mtd 里那三行的真身）：
    ★ 2026-10-12 二次定案（内核内建表 + 字节比对）已纠正本段旧说法：
      槽 A：槽头@+0、kernel @+0 (0x340000)、rootfs @+0x340000 (0x1220000)、版本头 @+0x1560000
            → 绝对：kernel@0x700000、rootfs@0xA40000、版本头@0x1C60000
      槽 B：同上整体 +0x1C00000
            → 绝对：kernel@0x2300000、rootfs@0x2640000、版本头@0x3860000（实测）
    ⇒ /proc/mtd 的 kernel1/kernel2/rootfs = **槽 A 内核 + 槽 B 内核 + 槽 A rootfs** 的平铺视图，
      **不是**"槽内有两个内核、rootfs 被推到 +0x680000"。内核表的槽层条目是
      kernel1=28M@0x700000、kernel2=28M@0x2300000、rootfs=(0,0) 占位符。
    ⇒ 两槽各带一份完整内核 + 一份 rootfs；不共享。
      另：rootfs 尺寸随固件代变化（6B5=0x1100000 / 7B5·8B8=0x1220000），版本头随之移动。

────────────────────────────────────────────
【3】要更正的三处
────────────────────────────────────────────
a) 我说"两个内核槽 + 一个共享 rootfs" → **错**。既不是"两内核槽"，rootfs 也不共享。
b) 项目记忆 MEMORY.md 里"H3600 那套『整槽 A/B + UBI + 双槽 sysupgrade』在 E2631 上一行都用不上"
   → **半错**。"整槽 A/B" E2631 本来就有；真正用不上的是 UBI 和那份 sysupgrade 脚本
   （E2631 是裸 mtdblock + JFFS2）。
c) 本机权威报告 §2.2 把"E2631 槽"写成 0x20A0000 / 0x3CA0000
   → 这两个数是**槽内版本头（verhdr）的物理地址**（6B5 代 = 槽起点 + 0x19A0000），
      **不是槽起点**。槽起点是包声明的 0x700000 / 0x2300000。
      两组数字都对但含义不同，报告里被当成同一个概念用了。
      另：8B8 代该位置实测为 FF ⇒ 版本头位置本身随固件代变化，不能当常量。

────────────────────────────────────────────
【4】对移植/刷机的影响
────────────────────────────────────────────
- E2631 与 SR1010 **同构** ⇒ cnjn 的做法（打成原厂包、用第二个固件槽、原厂槽保留可回退）
  理论上可以照搬，比原先判断的更乐观。
- ~~但有一个必须先解掉的冲突：国内插件分区的**声明范围**与槽 B 重叠~~
  ★ 本条已作废（2026-10-12 实测推翻，详见《E2631分区真实落点定案-2026-10-12.txt》）：
  /proc/mtd 只给尺寸不给偏移，"插件区 0x1FA0000–0x2FC0000 / 与槽 B 重叠 12.75MB"
  是把尺寸累加当偏移得出的**假坐标**。实测 kernel1=0x700000、rootfs=0xA40000、
  kernel2=0x2300000、UUPlugin=0x6F00000，插件区整包在 flash 尾部 0x6F00000–0x7EE0000。
  0x2A40000/0x2E40000/0x2FC0000 与各自的槽 A 镜像地址（0xE40000/0x1240000/0x13C0000）
  **逐字节相同** ⇒ 那些地址里住的是槽 B 自己的 rootfs。**槽 B 与插件区零交集。**
- ~~内核槽上限仍是 kernel1 分区 0x340000 = 3,407,872 B … H3600 超 57 KB，需裁剪~~
  ★ 已作废：0x33FDCC 是**官方包自己选择的布局值**，不是硬件上限。真上限是槽跨度 28 MiB。
- ~~8B8 槽内比 6B5 多一个 3.25MB 的 kernel2（与 kernel1 同镜像），把 rootfs 从 +0x340000
  推后到 +0x680000~~ ★ 已作废：kernel2 不是"槽内第二个内核"，它的物理基址是**槽 B 起点**
  0x2300000（= 另一个槽的内核区）。rootfs 仍在**槽 + 0x340000**（7B5 实测 0xA40000，
  E(mtd8@0)=flash@0xA40000），独立佐证：0xA40000 + 0x1220000 = 0x1C60000
  = versionstates.curverheaderaddr（该处确有版本头）。
