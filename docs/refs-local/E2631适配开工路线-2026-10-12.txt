【0】结论（先给）

  可以开始。而且今天这轮"分区落点定案"恰好拆掉了 stage-1 脚手架的
  **第 1 号拦路石** —— 三块地基现在都在手上，剩下的活是"设备树 + 实测值 + 集成"，
  不是"写驱动"。

  一句话概括现在的状态：
      能不能跑   → 地基已具备（同 SoC 同 CPU 核的上游 target 驱动全能直接用）
      怎么跑进去 → RAM 引导，今天就能走，零风险
      能不能存   → 只剩"槽头/版本头格式 + 写路径要在真机验一次"，
                   不再有"能不能跑"这一层的问题 —— 原厂内核在 flash 上本来就是
                   **明文 uImage**，cspboot 引导明文内核已被证实（见【4】末）

  路线选型（详见【4】）：**② 原厂包重打包 更简单** —— 它把"写 flash"整个外包给原厂
  升级器，且验证可以纯离线做；① 的独有工作（设备侧写路径）只能在真机上试错。
  但建议 **② 做入口、① 做终点**：第一版镜像同时编进 ① 的写路径，走 ② 刷上机，
  一次网页刷机两条路都拿到。

【2】stage-1 脚手架列的"三个写不了 flash 的理由"，现在的状态

  ①「分区布局未公开」 —— **已解**
     内核自带分区表：vmlinux @0x432358，15 条，步长 0x20，
     结构 {char *name; u32 pad; u64 size; u64 offset; u64 pad;}。
     不在 /proc/cmdline，也不在设备树。
     并已用原始 128 MiB dump 交叉验证：
       · cspboot 槽头（33 33 33 33 CC CC CC CC 88 88 88 88 DD DD DD DD）
         出现在 0x700000 与 0x2300000 —— 正是内核表自己叫 kernel1/kernel2 的两个地址；
       · flash@0x6E00000 与 mtdblock13 逐字节相同。
     ⇒ 完整表已抄进 DTS 的 flash@0 注释块（不再有"推断出来的偏移"）。

  ②「boot 镜像格式未确认」 —— **结构上已确认，行为上仍待证**
     两块槽基址都读到与 H3600 相同的 32 字节槽头 ⇒ 同一 bootloader 家族，
     "另一个槽可回退"这条恢复路径成立。
     尚未证明的是：**cspboot 愿不愿意引导一个明文槽**（见 ③）。

  ③「AES-128-ECB 透明解密」 —— **真实存在，但已限定范围**
     密钥 E263111559d0dfde：dump@0xA40000 解出合法 JFFS2 节点，与真机 /dev/mtd8
     逐字节一致；同一块在 0x2640000 复现（= 槽 B 的副本）。⇒ 原厂写路径确实加密。
     但它**碰不到 RAM 镜像**：RAM 引导不经过任何分区文件系统。
     剩下的是一个更窄的问题：明文槽能不能被引导 —— 这属于 stage 2 的写路径问题。

    TODO-N1  MDIO / GPHY 地址表：现在整块是从 H3600 抄的**假设**（phy 8/10/11/12/13）
    TODO-A1  MAC 地址来源：H3600 读 tag@0x1e；E2631 未验证（未验证前接口用随机本地管理地址）

    TODO-W1  PCIe reset/enable 引脚 + MT7916 校准数据偏移（stage-1 故意留 disabled）
    TODO-F1  SPI-NAND 频率：50 MHz / 2 线是抄 H3600（同 HYF1GQ4U 系列，但 E2631 是 UTACAE 非 UDACAE）

    · platform.sh 与分区表要**按 E2631 重写**（H3600 那套是 UBI + 完全不同槽位）

      ⇒ 现实路径是 fork + GitHub Actions（脚手架 workflow 已内建，改 OPENWRT_REPO/REF 即可）


【4】刷写路线选型：哪条更简单 —— 答：**② 更简单，但 ② 不是终点**

  先把两条路拆成"共同前段 + 各自独有的活"。共同前段占工作量的大头：

  ◆ 共同前段（两条都要，不可省）
      · DTS 集成（E2631 device + 分区表）
      · **SPI-NAND 读 + 挂载 rootfs** —— 注意这条两条路都要：rootfs 就住在同一片
        SPI-NAND 上，不管 flash 是谁写的，内核都得先把 nand 读起来才能挂根。
      · 有线网 L2 / PCIe + Wi-Fi L3
      ⇒ "选哪条"并不改变前段；先做 RAM 引导对两条都是净收益。

  ◆ 各自独有的活

    ┌────────────────┬──────────────────────────────┬────────────────────────────┐
    │                │ 路线 ① OpenWrt 自管 NAND     │ 路线 ② 原厂包重打包        │
    ├────────────────┼──────────────────────────────┼────────────────────────────┤
    │ 独有工作       │ 设备侧 擦/写 + 槽头写入      │ 包格式收口（全在 host 侧） │
    │                │ + platform.sh（重写布局）    │                            │
    │ 要 AES 吗      │ 不要（写明文、自己读明文）   │ 不要（原厂段是密文，但     │
    │                │                              │ 写回是"逐字节照抄"）       │
    │ 怎么验证       │ 必须在**真机上写 flash**     │ **纯离线**：工具 + 模拟器  │
    │ 已有模板       │ 有（H3600 的 slot-marker     │ 有（本机重封工具链 +       │
    │                │ + 双槽 platform.sh）         │ 24 步 web 刷机模拟器）     │
    │ 未知项         │ a) 写路径在 E2631 从未跑过   │ 验收门是否已全部掌握       │
    │                │ b) cspboot 对"非原厂写的      │ （离线可查，见下）         │
    │                │    槽头"的态度               │                            │
    │ 试错代价       │ 一次真机写 flash             │ 一次 web 上传 + 一次刷写   │
    │ 之后能自升级吗 │ 能（sysupgrade）             │ 不能（要再走一次 ② ）     │
    └────────────────┴──────────────────────────────┴────────────────────────────┘

  ◆ 为什么 ② 更简单 —— 三条硬理由

    1. **它把"写 flash"整个外包。** OpenWrt 侧不需要 NAND 写路径、不需要擦除逻辑、
       也不需要相信自己造的槽头是 cspboot 认的格式 —— 全由原厂升级器做。
       ① 里唯一"大"的那一块（设备侧写 + 槽头 + platform.sh），② 直接跳过。
    2. **它的验证是离线的。** 包格式收口可以在本机用 parse_zte_pkg.py + 模拟器做完再上机，
       改错了不烧 flash；① 的写路径只能在真机上试错。
    3. **它已经有一次成功先例。** cnjn 在 SR1010 上走的正是这条（打原厂包 → 原厂 web 刷）。

  ◆ 一条关键的"未知已消"（让 ② 的清单进一步缩短）

    早前担心"原厂升级器会不会重新加密/重写内容"，现在**已有答案：它逐字节照抄**。
    证据：`包内 rootfs 段`（密文）与设备 flash 上的 rootfs 段**逐字节相同**
    （AES-ECB 解密后 == 设备 mtd8 dump，两侧 md5 均为 `835653325cafa1c73d52e2baadd8d973`）。
    ⇒ 加密发生在**打包时**，不在刷写时。所以我们往包里放什么，flash 上就是什么。

  ◆ 为什么 ② 不是终点

    · ② 刷进去的 OpenWrt **自己不能升级 flash**（没有写路径）⇒ 每次更新都要重新打包 +
      网页上传一次。
    · overlay 得借原厂那份**明文 JFFS2 插件分区**（cnjn 就是这么做的：放 `/Plugin/.owrt`，
      原厂文件不动）。

  ◆ 最终建议：② 做入口，① 做终点，而且**可以一次到位**

    ② 只是"交付通道"，往里装的镜像内容不限。所以第一版镜像就**同时把 ① 的写路径编进去**
    （spifc/spi-nand 写 + overlay + sysupgrade + E2631 版 platform.sh），然后走 ② 刷上机：

      · 若 ① 的写路径自洽 → 一台机器同时拿到"能自升级"和"能破槽头回原厂"；
      · 若 ① 的写路径有问题 → ② 的通道仍把你救回原厂，零损失。

    ⇒ 一次网页刷机，两条路都拿到，且**不需要先赌 ① 能不能写**。

  ◆ 两条容易踩的点（记下）

    · 别想在 ① 里"复刻原厂加密"：**不需要**。原厂那层透明解密只存在于**原厂内核**里，
      你没在跑它；OpenWrt 写明文、OpenWrt 内核读明文即可。
    · 决定 ① 可行性的那条关键事实已经有了：**槽 A 的内核在 flash 上是明文 uImage**
      （uImage 魔数 + 双 CRC 都验过）⇒ cspboot 本来就引导明文内核。
      "明文槽能不能引导"这个顾虑基本解除，剩下的是**槽头 / 版本头格式**那一层。


【5】建议的第一批动作（今天/零风险）

  第 1 步  把 e2631-openwrt 建成仓库，push 到 GitHub，让 Actions 先跑 `dts` job（约 10 秒）
           —— 只为确认 DTS 能编过（含本次写入的分区注释块）。
           同时确认 workflow 里 OPENWRT_REPO/REF = ghahramani/openwrt @ pr-zte-zxhn-h3600。

  第 2 步  跑 `build` job 出 openwrt-sanechips-generic-zte_zxhn-e2631-initramfs.uImage。
           （第一次几乎一定会失败；按 CI 输错逐条修，这是 DTS/集成的正常节奏。）

  第 3 步  串口 0x94404000 / 3.3V TTL / 115200 8N1，上电按 1，输 cspboot 密码，
           setenv ipaddr 192.168.10.66 / serverip <PC>
           tftp 0x43000000 <initramfs.uImage> ; bootm 0x43000000
           **必须加载到 0x43000000**（加载到入口地址会走 uImage XIP，64 字节头压在内核
           入口上，静默崩溃）。全程不写 flash。

  第 4 步  看 6 条里程碑：earlycon/console 起来 → SMP 2 核 → l2c CACHE_ID
           → spifc 探测成功 + mtd0 为 128 MiB → MDIO 总线注册 → shell 提示符。

  第 5 步  把 tools/probe-e2631.sh 放 /tmp 跑一遍，收 MDIO / MAC / LED / 内存 实测值。

  第 6 步  用实测值把【3】的 5 个 TODO 填掉，出第二版 DTS。


【6】不会因为移植进步而消失的硬约束（沿用）

  · 用户态必须**软浮点 / arm EABI5**（armel）。已实测定案（2026-10-12 真机三条独立证据）：
    原厂内核 `# CONFIG_VFP is not set`；原厂 busybox 的 ELF `e_flags=0x05000202` 带 SOFT_FLOAT 位；
    加载器 `/lib/ld-uClibc-0.9.33.2.so`。
    （硬约束是"软浮点"，**不是 "armv5"** —— 本机 ISA 是 ARMv7-A。本 target 无 `fpu` 特性，
      出来的正是 soft-float，无需额外动作。）
  · 无 AES 硬加速 ⇒ 加密类负载（mihomo 等）单核封顶（社区实测 ~165 Mbps）
  · flash 带 AES-128-ECB 透明解密 ⇒ 只要动 NAND 持久化就绕不开
  · OpenWrt 对"未上游化的新 target"态度明确（维护者原话：chances extremely low）
    ⇒ 大概率长期挂在自建分支/自建源上

  三条不能破的操作规则：
  · TFTP 引导验证通过前，绝不写 flash
  · 镜像只进非活动槽，且在有 UART 兜底之后
  · 别把 H3600 的 sysupgrade.bin 直接刷进 E2631（board_name 校验会拒；
    -F 强刷会按 H3600 分区表把 UBI 写到你的 B 槽 + 配置区 ⇒ 砖，原厂回不去）
