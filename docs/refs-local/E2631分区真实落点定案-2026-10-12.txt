E2631 分区结构定案（第 2 版）—— 权威数据源：内核内建分区表 + 真机字节比对
2026-10-12   真机 192.168.5.3（V1.0.0.7B5.8000）；整片 e2631_no_oob.bin（6B5）

【0】结论（先给，三句）

  1. **你的判断是对的：E2631 = A/B 两个固件槽 + 一份独立的国内插件分区表。三者零交集。**
     "槽 B 与国内插件分区的声明范围重叠"这件事**不存在**，上一轮那句作废。
  2. 真正的分区表**既不在 /proc/cmdline，也不在设备树**，而是**编在内核镜像里**
     （vmlinux 偏移 0x432358 起，15 条）。本轮把它逐字节解出来了 —— 这是本项目的
     分区结构**唯一权威来源**。
  3. 关键澄清（这是前面所有翻车的根因）：
     **"kernel1 / kernel2 / rootfs" 这三个名字，在内核槽层表和 /proc/mtd 里含义不同。**
       · 内核槽层表：kernel1 = 槽 A（28 MiB）、kernel2 = 槽 B（28 MiB）、rootfs = 占位符 (0,0)
       · /proc/mtd ：kernel1/kernel2 = 两槽**各自槽内**的那份内核（3.25 MiB）；
                     rootfs = **活动槽槽内**的那份 rootfs（18.125 MiB）
     ⇒ 同名不同义、且 /proc/mtd 不给偏移列 —— 任何"按名字/尺寸累加推偏移"的做法必然翻车。


【1】权威数据源：内核内建分区表（A 级）

  位置：vmlinux 文件偏移 **0x432358**，15 条，步长 **0x20**
  结构：{ char *name; u32 pad; u64 size; u64 offset; u64 pad; }
        name 指针值 = 0xC0008000 + 字符串在 vmlinux 的文件偏移
        （例：0xC053A6DC ↔ vmlinux@0x5326DC = "Whole flash"，与 .rodata 串池完全吻合）

  vmlinux 从哪来（可复现）：
    kernel1 分区 = [0x20 槽头][uImage 64B][zImage][追加 DTB]
    zImage 内偏移 0x65A8 处是 **gzip 流**（b'\x1f\x8b\x08'，wbits=47）
    gzip 解开 → **6,667,040 字节（0x65BB20）** 的 ARM Image（load base = 0x40008000）
    工具：tools/find_parttable.py（解压 + 搜名）、tools/dump_parttable.py（按步长解析）

  逐字节解出的原始表（name / size / offset 均为实测值）：
  ┌──────────────┬──────────────┬──────────────┐
  │ name         │ size         │ offset       │
  ├──────────────┼──────────────┼──────────────┤
  │ Whole flash  │ 0x08000000   │ 0x00000000   │
  │ Bootloader   │ 0x00100000   │ 0x00000000   │
  │ tag          │ 0x00100000   │ 0x00100000   │
  │ wifi         │ 0x00100000   │ 0x00200000   │
  │ usercfg      │ 0x00200000   │ 0x00300000   │
  │ defcfg       │ 0x00200000   │ 0x00500000   │
  │ kernel1      │ 0x01C00000   │ 0x00700000   │  ← 28 MiB = 槽 A
  │ kernel2      │ 0x01C00000   │ 0x02300000   │  ← 28 MiB = 槽 B
  │ rootfs       │ 0x00000000   │ 0x00000000   │  ← 占位符（rootfs 在槽内）
  │ UNIFIED      │ 0x00100000   │ 0x06E00000   │
  │ UUPlugin     │ 0x00500000   │ 0x06F00000   │
  │ DPIPlugin    │ 0x00300000   │ 0x07400000   │
  │ JDXBPLUGIN   │ 0x00180000   │ 0x07700000   │
  │ owdptsbin    │ 0x000A0000   │ 0x07900000   │
  │ status       │ 0x00500000   │ 0x07A00000   │
  └──────────────┴──────────────┴──────────────┘
  注：表中 kernel1/kernel2 的 **28 MiB 与官方升级包 verhdr 声明的槽 base/span
      （0x700000/0x2300000, span 0x1C00000）逐字段一致** —— 两条独立证据互咬。
  /proc/mtd 的声明顺序与之不同的点：表中 UUPlugin 在 owdptsbin/status 之前，
      物理上 UUPlugin→DPIPlugin→JDXBPLUGIN→(512K 空隙)→owdptsbin→(384K 空隙)→status。


【2】三层结构（分开说，不要混）

  层 1 · 整机槽（内核表直接给出）：
      槽 A（表名 kernel1）  [0x00700000, 0x02300000)  28 MiB
      槽 B（表名 kernel2）  [0x02300000, 0x03F00000)  28 MiB
      rootfs 在槽层 = (0,0) ⇒ **rootfs 不是独立区间，它在每个槽里面**
      ⇒ "两槽共享一份 rootfs"彻底否掉：是**每槽各带一份完整内核 + 一份 rootfs**。

  层 2 · 槽内组件（= /proc/mtd 的 kernel1 / kernel2 / rootfs 的真身）：
      槽 A： [0x20 槽头][kernel1 @0x700000, 0x340000][rootfs @0xA40000, 0x1220000]
             [版本头 @0x1C60000][空闲到 0x2300000]
      槽 B： [0x20 槽头][kernel2 @0x2300000, 0x340000][rootfs @0x2640000, 0x1220000]
             [版本头 @0x3860000][空闲到 0x3F00000]
      ⇒ 0x2640000 − 0xA40000 = 0x1C00000 = 槽跨距；0x3860000 − 0x1C60000 = 0x1C00000 ✓
      ⇒ /proc/mtd 的 kernel1/kernel2/rootfs 就是"槽 A 内核 + 槽 B 内核 + 槽 A rootfs"
        平铺出来的三行 —— 不是顺排，也没有共享。

  层 3 · 国内插件区（尾部，与两个槽零交集）：
      [0x06E00000, 0x07F00000) 共 17 MB 预留，6 个分区实际占 16.125 MB，尾 1 MB 未用


【3】实测验证（四条独立判据，全部命中）

  V1 槽 A 基址 = 0x00700000
     e2631_no_oob.bin@0x700000 = 33 33 33 33 cc cc cc cc 88 88 88 88 dd dd dd dd ← cspboot 槽头
  V2 槽 B 基址 = 0x02300000
     e2631_no_oob.bin@0x2300000 = 33 33 33 33 cc cc cc cc 88 88 88 88 dd dd dd dd ← 同一槽头
     （两个槽头都出现在**内核表自己声明的** kernel1/kernel2 地址上 —— 互为印证）
  V3 UNIFIED 基址 = 0x06E00000（本轮新增，决定性）
     真机 flash@0x6E00000 = 85 19 01 e0 35 00 00 00 4a 4e e0 cd 01 00 00 00
                            98 25 00 00 00 00 00 00 59 75 cc 6a 0d 00 00 00
     真机 mtdblock13@0   = 85 19 01 e0 35 00 00 00 4a 4e e0 cd 01 00 00 00
                            98 25 00 00 00 00 00 00 59 75 cc 6a 0d 00 00 00   **逐字节相同**
  V4 UUPlugin = 0x06F00000、owdptsbin = 0x07900000（前轮实测，本轮复核）
     mtdblock9@0x300000 与 flash@0x7200000 逐字节相同（0x7200000−0x300000=0x6F00000）
     注：本地 6B5 dump 里插件区唯一的数据块在 0x72C0000–0x72E0000（= UUPlugin+0x3D0000），
         其余全为擦除 —— 与真机 7B5（mtd9@0x300000 有 jffs2 节点）属两代差异，不矛盾。
  V5 其余三个分区（DPIPlugin/JDXBPLUGIN/status）在声明地址处与器件视图同为擦除：
     真机 flash@0x7400000 = FF / mtdblock12@0 = FF   （DPIPlugin   0x7400000）
     真机 flash@0x7700000 = FF / mtdblock14@0 = FF   （JDXBPLUGIN  0x7700000）
     真机 flash@0x7A00000 = FF / mtdblock11@0 = FF   （status      0x7A00000）
     ⇒ "FF↔FF 一致"不能单独定案，但**与 V3/V4 的字节命中联合后**，整表闭合。

【5】旧"按尺寸累加"错在哪（第 6 次同源，本轮升级为第 7 次线索）

  错误链条：
    /proc/mtd 只有 size/erasesize/name 三列 → 我假设"第 N 个分区偏移 = 前 N−1 尺寸之和"
    → 得出 UUPlugin@0x1FA0000 / status@0x2540000 / … / JDXBPLUGIN@0x2FC0000
    → 其中 6 个落在槽 B 范围内 → 于是我宣称"槽 B 与插件区重叠 12.75MB"（虚构）。

  本轮实测反证（真值 vs 累加猜测）：
    UNIFIED    真值 0x06E00000  累计猜 0x07C60000   差 14.125 MB   ← 猜错
    UUPlugin   真值 0x06F00000  累计猜 0x01FA0000   差 71.00 MB    ← 猜错（碰巧也对不上）
    DPIPlugin  真值 0x07400000  累计猜 0x07960000   差 5.375 MB    ← 猜错
    JDXBPLUGIN 真值 0x07700000  累计猜 0x07D60000   差 6.375 MB    ← 猜错
    owdptsbin  真值 0x07900000  累计猜 0x024A0000   差 83.00 MB    ← 猜错
    status     真值 0x07A00000  累计猜 0x02540000   差 84.00 MB    ← 猜错
  （前轮"UUPlugin=0x6F00000 / owdptsbin=0x7900000 碰对"是因为那两条恰好被独立字节比对
   命中，而不是累加算对。）

  根因两条，都必须记死：
    a) /proc/mtd **没有偏移列**，偏移只能由内容比对或权威表得到；
    b) **同名不同表**：kernel1/kernel2/rootfs 在槽层表与 /proc/mtd 里指的不是同一样东西，
       拿 /proc/mtd 的名字顺序去推 flash 物理顺序，前提本身就不成立。

【7】对移植/刷机的影响（替换旧"障碍 3"）

  ✅ 旧障碍 3（"槽 B 与插件区重叠 12.75MB，写前需探边界"）**彻底删除**。
     槽 B 整段 28 MiB 都是原厂槽内容，可按槽布局整段使用。
  ✅ 插件分区全部位于 0x6E00000 之后，与槽布局完全解耦。
  ✅ 回退路径干净：不动槽 A（0x700000 与 0xA40000 两处）即保留完整原厂固件。
     OpenWrt 可放槽 B，或自建分区表放中部 47 MB。
  ⚠ 若把 OpenWrt 的 rootfs 写进槽 B 的 rootfs 区（0x2640000），会覆盖原厂那份备份镜像
     —— 原厂"两槽互为备份"就只剩槽 A。想两全：内核放槽 B、rootfs/overlay 放中部 47 MB。
  ⚠ 原厂 rootfs 分区在 flash 上是 **AES-128-ECB 密文**（内核读路径透明解密），
     mainline 读到的就是密文 ⇒ 分析前必须离线解密；OpenWrt 自己写文件系统不需要加密。
     插件分区则是**明文 JFFS2**（实测 flash 视图 == mtd 视图），无需任何处理。

【9】这次踩的坑（第 6→7 次同源，规则再升级）

  前 5 次：拿"分区名字 / 挂载表 / 第三方资料"当结构结论。
  第 6 次：拿"表里只有尺寸，却把尺寸累加当偏移"。
  第 7 次（本轮）：**同一个词在不同表里含义不同**（kernel1/rootfs 在槽层 vs 槽内层），
                    却把两张表的行当同一列来对齐。

  规则（补充进 MEMORY.md）：
    · 分区偏移只能来自：① 权威表（内核/包声明，且要有原文位置）；② 内容比对实测。
      尺寸、顺序、名字 —— 三者都不能推偏移。
    · 引用"某分区叫什么"之前，先问一句：**这是哪张表里的名字、这张表是哪一层？**
      词同而层不同，必须显式标注（如 "kernel1[槽层]" vs "kernel1[/proc/mtd]"）。
    · 找到权威表后，仍要用至少一个**内容比对**去校验它（本轮 V3 就是这么定案的）。

【10】附带更正：rootfs 加密基址 = 0xA40000（不是旧记的 0xD80000）

  在 e2631_no_oob.bin 上实测（key `E263111559d0dfde`，AES-128-ECB）：
    raw@0x0A40000 = 20 7c a1 cc 09 2a b5 46 40 75 5e c6 9d 1d 46 8e
    AESdec        = 85 19 01 e0 31 00 00 00   ← 与设备 mtd8@0 **逐字节一致** ⇒ 基址 = 0xA40000 ✔
    raw@0x2640000 = 20 7c a1 cc …（同上）    → AESdec 同为 85 19 01 e0 ⇒ **槽 B 的 rootfs 镜像** ✔
    raw@0x0D80000 = 3f c3 4e 4d 96 42 0f b3   → AESdec = 85 19 02 e0 21 03 00 00
  注意最后一行：0xD80000 落在 rootfs **内部**，AES 解密后照样得到一个"看着像 JFFS2 节点"
  的头 —— 所以**"解密出合法 magic / 熵值 8.0"都不足以判定分区基址**。
  基址只能用"mtd 设备视图 ↔ 整片 dump 逐字节比对"来定。（旧记 `rootfs@0xD80000` 已更正。）
