0. 一句话结论
================================================================================
ZX279128S 这颗 SoC 的 OpenWrt/主线适配，在 2026-09 月底到 10 月中之间发生了质变：
H3600 那条线已经把 6.18 的完整驱动栈（SMP / 时钟 / GPIO / PCIe / MDIO / 以太网 + PPE 硬件转发 /
硬件交换 / SPI-NAND+UBI / USB3 / Wi-Fi 6）全部打通并在真机验证，但 PR #25469 至今 open 未合，
OpenWrt master 里还没有 target/linux/sanechips。
E2631（你自己的仓库）停在"内核起来、驱动为 0"的阶段，README 已过期（写在 08-31），
树里其实已经放进了 cnjn 的整套 ZX279133 网络驱动，并在 09-27 修了 3 个真实的数据面 bug。
最大的信息增量：F670L recon 仓库明确把 E2631 项目列为"两个被同一份材料卡住的项目"之一，
并已经把你说的下一步（逆向 tm.ko）所需的 tm.ko / switch.ko 连同完整符号表公开了。
=> 现在的正确姿势不是再自己逆向，而是「抄 H3600 的驱动栈 + 用 recon 的符号表对齐寄存器语义」。

1. 四条线的关系（同一颗 SoC，四块不同的板）
================================================================================
板子              厂商/渠道          形态          RAM/Flash            无线          状态
----------------  ----------------  ------------  -------------------  ------------  --------------------------
ZXHN H3600 (V9)   Hyperoptic UK     家用网关      512MB/128MB SPI-NAND  MT7915D       OpenWrt 6.18 全功能跑通
ZXHN H1600        同上              同门型号      同上                  MT7915D       同一 target 支持
ZXHN E2631        中兴 巡天AX3000   家用路由器    256MB/128MB SPI-NAND  MT7916/7976   主线 6.18.38 只到 shell
ZXHN F670L        Airtel India      GPON ONT      512MB/128MB           MT7603E+MT7663 仅侦察，未启动移植
SoC 统一为 ZX279128S：双核 Cortex-A9 @1GHz（ARMv7-A），用户态**软浮点 / arm EABI5**
（原厂内核 `# CONFIG_VFP is not set`、用户态 ELF e_flags=0x05000202 带 SOFT_FLOAT 位，
2026-10-12 真机三重实测；注意 ISA 是 ARMv7 而非 armv5），无硬件 AES。

关键事实：外设 compatible 字符串在整个板族里是稳定的（recon 仓库已用真机 DT 逐条比对）：
  zte,ZX279127-uart · zte,iram · arm,cortex-a9-gic · arm,cortex-a9-global-timer
  arm,pl310-cache · arm,cortex-a9-twd-wdt · zte,zx279128s-mdio · zte,ZX279127-dwc2 · snps,dwc3
其中 MDIO 连地址都一样：mdio@9a101000 reg=<0x9a101000 0x18>。
唯一"同块不同用"的：0x92000000 + 0x400000 —— H3600 当以太网 MAC（gmac），F670L 原厂当 pon@92000000。

2.2 Medium 长文 — Resurrecting ISP E-Waste（作者同 Ghahremani）
--------------------------------------------------------------------------------
主线：£15~20 的二手 Hyperoptic H3600（原厂 Linux 4.1.25 载波固件）→ 16 天 → 主线 Linux 6.18 + OpenWrt。
阶段与坑（按文章顺序）：

① 破壳拿 root / 备份
   原厂 web 漏洞拿到临时 root → 逐分区 dd 出来 tftp 上传，保住 bootloader.bin / wifi 校准 / tag 凭据。

② bootloader 密码（这一段是"AI 破局"的招牌）
   在 bootloader.bin 偏移 0x5b3c3 找到 *** Please input bootmode password: *** 紧邻的
   20 字节硬编码 SHA-1：4A746281E9135F96E0777E658C08015ECEF42440
   SHA-1 不可逆，只能猜；按中兴芯片命名习惯构造掩码爆破，命中：
     输入 Boot4128s!  →  SHA1 = 4a746281e9135f96e0777e658c08015ecef42440（完全一致）
     构成 = Boot + 4128s（ZX279128S 的内部硅片标识）+ !
   输入即掉进不受限的 U-Boot（2013.04，板型 zx279128sevb，cspboot #）。

③ 从零写 target/linux/sanechips
   反编译 flash dump 里的扁平设备树（FDT），重建：内存映射（0x40000000，512MB DDR3）、
   pinmux、时钟树、外设基址 → 写成 zx279128s.dtsi + zx279128s-zte-zxhn-h3600.dts；
   双核 A9 SMP 上核、GIC-400、硬件定时器、复位线；U-Boot TFTP 纯 RAM 迭代（不写 flash）。

④ 最硬的 bug：L2C-310 外部缓存写缓冲未排空 vs PCIe MMIO 读
   现象：冷启动 mt7915e 报 "Message 00000010 (seq 1) timeout / Failed to start MCU firmware"，
   或大文件传输中无线直接掉总线；网上那些"加 timeout、重插模块"全无效。
   根因：Cortex-A9 不会自动 snoop PCIe bus-mastering。MT7915 通过 PCIe DMA 写状态字到内存并置中断，
   但 CPU 在外层 L2C-310 里的写缓冲还没排空到物理 DDR3 时就执行了 MMIO 寄存器读 →
   读到过期状态字 → 判定 MCU 死了 → 直接把 PCIe 链拉掉。
   修法（进入上游补丁形态）：在 mt76 和 Sanechips PCIe 驱动里加显式外层缓存栅栏：
     outer_sync(); mb();   /* Ensure outer L2 cache write-buffer drainage before PCIe MMIO read */
   结果：MCU 超时彻底消失，双频 802.11ax 稳定跑满千兆无线、零丢包。
   对应 PR 里的 patches-6.18/004 + 005（"l2c: Serialize device reads with cache maintenance"）
   和 package/kernel/mt76/patches/001-wifi-mt76-serialize-register-reads-with-outer-cache.patch。

⑤ PCIe PERST# 有效极性 + DWC LTSSM 重训
   MT7915 重启后偶发消失。用 devmem 探寄存器发现 DWC 控制器因 PERST# 低有效极性反了而一直把卡按在复位。
   修 reset 断言逻辑 + 加显式 LTSSM 重训循环 → 每次开机都能稳定协商到 Gen2。

⑥ 逆向硬件 PPE：940+ Mbps
   把 SoC 里的硬件包转发引擎和硬件 LAN 交换接上 Linux switchdev/phylink、中断驱动 NAPI、
   每 CPU 统计、ethtool MAC/RMON 计数。开关走 UCI（/etc/config/hw_switching + procd 服务）
   或 sysfs（echo 1 > /sys/devices/platform/soc/92000000.ethernet/hw_switching），
   不依赖 LuCI；LuCI 勾选框通过补丁包提供（因为 luci-app-firewall 是核心包，上游不愿合硬件专属开关）。

⑦ 工具链现实（值得注意）
   作者明确写了：OpenAI Codex 即便付费 Pro 也频繁撞配额（5 小时锁、周限额），
   在需要跨数千行内核驱动/头文件/寄存器 dump 的深水区不可用；
   最终靠 Claude Code + Antigravity 的大上下文多文件重构撑住。
   ——这条对你是直接可用的经验：这类活必须用能一次吞下整棵驱动目录的模型。

4. 对你（E2631）最有价值的 6 件事，按优先级
================================================================================
1) **不要再去逆向 tm.ko**。H3600 那条线已经把同一颗 SoC 的以太网 + PPE + 硬件交换写成了可读的 C
   （zx279128s-main.c / ppe.c / switch.c，共 2.6K 行，patches-6.18/019~020），
   F670L recon 仓库也把你的项目明确列为"被同一批材料卡住"并公开了 tm.ko/switch.ko 的完整符号表。
   正确做法：拿 H3600 的驱动当**语义字典**，用 switch.ko 的 214 个具名函数
   （ethdrv_port_dev_*、ethdrv_set_wanportid、hf_set_l3_entry…）对齐寄存器含义。
2) **先接 MDIO + PHY，这是最小可验证单元**。MDIO 地址 0x9a101000 在两块板上完全一致、
   compatible 相同（zte,zx279128s-mdio），你的 DT 里节点都写好了只是 disabled。
   E2631 的 GPHY 块在 0x9b000000/9b100000/9b200000/9b300000（4 个），PHY 地址需探。
3) **DT 是当前唯一的真实缺口**。驱动搬进来了（09-27 还在修数据面），但 e2631.dts 里
   mdio/gephy/pcie/nand/spifc 全 disabled、cpus 只有 cpu@0。
   照 H3600 的 patches-6.18/025（SoC dtsi 417 行）+026（板级 393 行）改写即可。
4) **第二核 SMP**：抄 platsmp-zx279128s.c（173 行）——这是把 165Mbps 天花板往上抬的唯一办法，
   而且你的 DTS compatible 里已经写了 "zte,zx279128-smp"（原厂 enable-method）。
5) **PCIe 通了才有 Wi-Fi**：MT7916 驱动已编进内核，只差 pcie-zx279128s.c + DT 节点。
   同时务必一起带上 L2C-310 的设备读串行化（patches 004/005 + mt76 patch 001），
   否则会复现 mt7915/7916 的 MCU 超时与随机掉卡。
6) **README 该更新**。它现在写着"有线网络驱动 ❌ 未开始"，但树里已有整套 ZX279133 网络驱动且
   09-27 修过 3 个真实 bug —— 对外沟通与接手者判断都会被误导。

================================================================================
5. 风险 / 不可控项（不因为移植进步而消失）
================================================================================
· 硬件无 AES 加速 + 软浮点 + 当前移植只跑 1 核（原厂侧双核在线）→ 加密转发/科学上网天花板低（社区实测 165Mbps 上限）。
· 无 VFP/NEON（原厂 `# CONFIG_VFP is not set` + 用户态 ELF e_flags 带 SOFT_FLOAT 位 + ld-uClibc，
  2026-10-12 三重实测；并与 08-31 自建 6.18.38 的 Features 行交叉印证）
  → 用户态一律 soft-float / arm EABI5（zig arm-linux-musleabi 静态编译，或原厂 uClibc 0.9.33.2）。
  ⚠ 是"软浮点"，**不是 "armv5"** —— ISA 层级是 ARMv7-A。
· flash 带 AES-128-ECB 透明解密，密钥由 zte_token 派生 —— 一旦要动 NAND 持久化就绕不开，
  这也是 H3600 那条线之外唯一"必须自己解"的部分。
· OpenWrt 对"未上游化的新 target"态度明确：维护者原话"chances … extremely low"。
  即便 H3600 合了，E2631 仍要自己走一遍板级文件 + 上游化，或者就长期挂在自建分支/自建源上。
· 温度/长期稳定性：社区对这颗 SoC 的评价就是"本来就热"，满载长期跑要自己观察。
