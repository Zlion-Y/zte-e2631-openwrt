## 1. 拒绝点的完整分类（验收 B）

所有进入 `ppe_add_skip` 计数的路径都汇在 `zx_ppe_block_cb()`
（`target/linux/sanechips/files/drivers/net/ethernet/zte/zx279128s-ppe.c:721-723`）：
`zx_ppe_flow_add()` 返回 `-EOPNOTSUPP` 即计数。返回该值的条件，按
数据流顺序：

| # | 行号（ppe.c） | 条件 | 分类 |
|---|---|---|---|
| ① | 313-324 | 规则携带 `FLOW_DISSECTOR_KEY_META` 且 `ingress_ifindex` 不是 5 个交换口之一 | **软件防呆包裹的硬件通路约束** |
| ② | 326-334 | `addr_type != FLOW_DISSECTOR_KEY_IPV4_ADDRS`（IPv6 流） | 软件策略（键/表格式约束） |
| ③ | 336-343 | `n_proto != htons(ETH_P_IP)` | 同上 |
| ④ | 344-345 | `ip_proto` 不是 TCP/UDP | 软件策略 |
| ⑤ | 347-349 | 缺 IPV4_ADDRS 或 PORTS 键 | 同上 |
| ⑥ | 398-399 | mangle 动作类型不在 ETH/IP4/TCP/UDP 内（注释原话 "VLAN, PPPoE and tunnel encapsulation are not supported"） | 软件策略 |
| ⑦ | 413-414 | 动作目标 `odev` 不是交换口 netdev（`zx_eth_is_port()`） | 硬件通路约束（同①） |

**WiFi 流命中 ①（及 ⑦）**：mt7916 的入向帧经 PCIe 直达 CPU 内存，从不经过
交换织物（SBRG）的入口；分类器的哈希表只在交换口入向上被查询。放宽 ①
的 if 判断（让 wlan netdev 通过 META 校验）**不会让任何帧被硬件转发**——
因为根本不存在「硬件看到这帧」的通路。所以：

- **①⑦ = 硬件端口号强约束（数据通路），不是可放宽的软件策略**；
  放宽需要硬件配合（让 WLAN 帧改道交换口入向，或用独立的加速引擎）。
- **②-⑥ = 可放宽的软件策略**，但它们拦的是 IPv6/PPPoE/VLAN 这类格式问题：
  键格式（`zx_ppe_halfwords()`，ppe.c:139-150）把 IPv4 地址写死在键里，
  分类器索引/规则表 `zx_ppe_v4_index`/`zx_ppe_v4_rule`（ppe.c:547-555，
  取值注释 "Values from the stock firmware"）是 IPv4 专表。放宽它们意味着
  给分类器造 IPv6 键表——即原厂的做法。

## 2. 与原厂行为的对照（对齐评估）

原厂在 4.1.25 内核上实现 WiFi 千兆，靠的是**私有 IDM/NPP 引擎**，不是
mainline `nf_flow_table`/`TC_SETUP_FT`（zwzzrl 2026-10-27 拆解：stock
vmlinux 中这些字符串出现 0 次；引擎寄存器视图见
`docs/refs-local/E2631原厂硬件视图-2026-10-12.txt`：npp@921c0000、
idm@921c8000 运行期 UP）。原厂分类器**有 IPv6 能力**（per-class NPU caps
`npu_ipv6_l3tcp{up,down}_cap`、IPv6 SNAT/DNAT RAM、NPTv6、本地 IPv6 地址
寄存器组）——即原厂对「WiFi 入向」和「IPv6 键」两个问题各有一条我们
没有的数据通路。

兄弟平台可读源码（`zx279133-idm.c` 38KB / `zx279133-np.c` 60KB /
`zx279133-tm.c` 29KB）说明**不必纯反汇编起步**，但接口差异清单（验收 C
要求的 ≥5 条：DMA 描述符格式、NAPI 注册方式、skb 归属与释放时机、流表
老化回调、与 mt76 的入向挂钩点等）需要逐行比对 vendor `.ko`（4.1 ARM32，
symtab 已拉齐可核）——工程量在「人周」量级起。

## 3. 分步结论

1. **「调 switchdev/VLAN 解决 WiFi 慢」确认为死路**（与清单已知易错点
   一致）：WiFi 流被 ①⑦ 拒绝属数据通路约束。
2. **「扩 PPE 键表支持 WiFi」不成立**；「扩键表支持 IPv6（走交换口的
   IPv6 硬转）」在软件策略层可行，但需要造 IPv6 索引/规则表与流表项——
   原厂设计量级（清单所谓「大改」）。
3. **WiFi 突破 ~200 Mbit/s 的唯一路径 = 复刻/重建 IDM/NPP**，前置 P0-1
   闭环（WiFi 稳定性）后才值得投入。本文不下 go/no-go。
4. 已落地的相邻修复（非本项交付物，见 commit f6effe3）：IPv6 ethertype
   trap 在 PPE 激活时恒开——修的是「有线 IPv6 被硬转路径断流」，不是
   WiFi 加速。
