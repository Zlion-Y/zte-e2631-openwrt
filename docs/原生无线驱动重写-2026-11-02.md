# 原厂无线驱动重写线（native）· 完整记录

> 本文记录一条**独立于主固件**的实验线：不用 mt76，按中兴原厂 4.1.25 二进制为唯一行为
> 规范，在 6.18 上重写 MT7916 的私有无线栈。
>
> 结论先说：**固件能起、校准能上传、band0 的配置命令全部被接受、数据帧能被 DMA 取走，
> 但截至本记录没有任何一帧被证明真的出现在空中**。当前卡点与已排除的假设在 §6、§7。
>
> 代码在 `native` 分支；主分支的固件不依赖本文任何内容。

## 1. 为什么要重写

主固件跑的是 mt76（`mt7915e`），能当双频 AP 用，但它是"按 mt76 的抽象去驱动 MT7916"：
WFDMA 环、MCU/WA 双核、私有 TXD、PPE 侧联动，全被封装在通用层里。native 线的目标是
把这些层显式写出来，等价于原厂 `mt_wifi` 驱动，从而：

- 无线侧也能走上 SoC 的硬件加速（PPE/NPU），而不是 mt76 的纯 CPU 路径；
- 行为可对照：任何一处拿不准，就去 `mt7916.ko` 里读，而不是猜；
- 不受 mt76 的上游节奏约束。

## 2. 方法论

| 项 | 做法 |
|---|---|
| 唯一规范 | 本板原厂 `mt7916.ko`，5.5 MB，**未 strip**，25 345 个符号 |
| 对照实现 | 上游 mt76（`mt7915/` + 公共层，约 40.7 k 行） |
| 工具 | `native/tools/re/armdis.py`（按符号反汇编，带重定位注解）、`findval.py` |
| 证据等级 | **S** 静态确证 / **B** 行为确证 / **I** 推断 |
| 铁律 | 字段表读全 → 手算期望值 → 再刷机验证；不以硬件试错代替阅读 |

关于工具：宿主 binutils 是 x86 的，`objdump`/`objcopy` 都不认 ARM，所以 ELF32 段表与
`.symtab` 是自己解析的，只依赖 capstone。重定位必须以**注释**形式还原，否则
`bl` 全部解成"跳到自身"，不可读：

```
bl  -> hif_io_write32
movw r1, #0  -> pci_kick_out_data_tx
```

`--callers` 还必须解析 `.data` 里的函数指针——这套 SDK 的 HAL 调用全走 ops 表，
`.text` 里根本没有对应的 `bl`。

> **结构性限制**：正因为是 ops 表驱动，静态调用图到不了叶子。凡涉及
> `ldr r3,[ops,#0xNN]; bx r3` 的地方，只能靠函数名 + mt76 对照推断（标 I）。

## 3. 时间线（含失败）

版本号是唯一的进度标尺，每个版本对应一次刷机。这段路上**大部分时间花在纠自己的错**，
而不是"破解原厂"。

| 版本 | 事件 |
|---|---|
| 3.19–3.25 | TXD 布局连错三次：`ctrl` 放错到 `+12`、步长写成 36 字节 |
| 3.30 | PCIe/HIF 翻窗 + `pci_set_master` —— DMA 引擎活的第一步 |
| 3.32–3.37 | FWDL 传输层（SemGet / AddressLen / FwScatter / Finish） |
| 3.74 | **`fw-state = 7`**：WM 9 段 + WA 3 段全下发，两个 FwStart 被接受 |
| 3.78–3.80 | RDY 后命令面打通：命令必须投 qid20；RX 环 CPU_IDX 写 `(didx-1) % depth` |
| 3.81–3.85 | efuse 四条路全空 → 改走厂商 `MT7916_EEPROM.bin`；`EFUSE_BUFFER_MODE` 4 页上传全 `ret=0` |
| 3.86 | `CHANNEL_SWITCH` 的 `rx_path` 传成掩码 → **WA 核卡死**，只能重刷恢复 |
| 3.87–3.88 | band0 起来（MAC/DEV/CHAN/BSS 全 `ret=0`）；发现 `status[]` 16 KiB 被 hex 挤爆 |
| 3.89–3.90 | TXD 全套落地；第一帧进 qid18，引擎报 `dma_done` |
| 3.91–3.92 | BSS 自己的 `STA_REC`（含 `WTBL_RESET_AND_SET`）+ `SET_DRR_CTRL`；出现"RX 只投递一次" |
| 3.93–3.94 | 按原厂语义武装 RX 环（`depth-1`）——仍然 0 投递 |
| 3.95–3.96 | **环号错了**：`0x18024520` 是 MCU_WA_MAIN（TX-free 事件环），数据环是 `0x18024540`；qid2 需主机武装 |
| 3.97 | **数据帧必须两段 DMA**（TXD 一段 + 帧一段，`LAST_SEC1`）；描述符终于字节正确 |

## 4. 已确证的数据面事实

### 4.1 环映射（`enum mt7915_txq_id` / `enum mt7916_rxq_id`）

| TX | 寄存器 | | RX | 寄存器 |
|---|---|---|---|---|
| FWDL 16 | `0x18024400` | | MCU_WM 0 | `0x18024500` |
| MCU_WM 17 | `0x18024410` | | MCU_WA 1 | `0x18024510` |
| BAND0 18 | `0x18024420` | | MCU_WA_MAIN 2 | `0x18024520` |
| BAND1 19 | `0x18024430` | | MCU_WA_EXT 3 | `0x18024530` |
| MCU_WA 20 | `0x18024440` | | **BAND0 数据 4** | **`0x18024540`** |
| | | | BAND1 5 | `0x18024550` |

地址公式 `0x18024500 + idx*0x10`（`MT_RING_SIZE = 0x10`）。原厂
`chip_show_dma_info()` 逐个 dump 六个 RX 环，与此一致。

**qid2 是 band0 的 TX-free 通知环**，固件不武装它（读回 `base=0`），必须主机来。

### 4.2 环形寄存器与初值

每环四个寄存器 `base / cnt / cpu_idx / dma_idx`，原厂 `mt_asic_init_txrx_ring` 的初值
**TX 与 RX 不同**：

```
TX/MCU 环：base <- desc_dma ; cpu_idx <- 0       ; cnt <- depth
RX 环    ：base <- desc_dma ; cpu_idx <- depth-1 ; cnt <- depth    (顺序 base→IDX→CNT)
```

原厂 RX 环结构的字段（用于对照）：

| 偏移 | 含义 |
|---|---|
| `+0x14` | depth |
| `+0x4c` / `+0x50` | base / cnt 寄存器地址 |
| `+0x3c` | cpu_idx 寄存器地址 |
| `+0x34` | 发布到 cpu_idx 的**值**（初值 `depth-1`） |
| `+0x08` | dma_idx 寄存器地址 |

`pci_rx_dma_done_handle` 的尾部就是 `write32(hc, ring[+0x3c], ring[+0x34])`；
`dump_dma_rx_ring_info` 的 pending 算术为 `dma_idx - cpu_idx - 1 (mod cnt)`，
即武装后为 0（空环）——与 mt76「填 `ndesc-1` 再 kick `q->head`」等价。

### 4.3 描述符（16 字节）

| 偏移 | 字段 |
|---|---|
| `+0` | `buf0` 缓冲 DMA |
| `+4` | `ctrl`：`SD_LEN0`(29:16) + `SD_LEN1`(13:0) + `LAST_SEC0`(30) + `LAST_SEC1`(14) + `DMA_DONE`(31) |
| `+8` | `buf1` 缓冲 DMA |
| `+12` | `info` |

**MCU 命令帧是单段**（32 字节头就是消息开头），`LAST_SEC0`；
**数据帧必须两段**：`buf0=TXD(32B) SD_LEN0=32`、`buf1=帧 SD_LEN1=len`、`LAST_SEC1`。

### 4.4 TXD（32 字节 = 8 dword）

| dword | 字段 |
|---|---|
| w0 | `TX_BYTES(len+32)` \| `PKT_FMT(CT=0)` \| `Q_IDX(AC00=0)` |
| w1 | `LONG_FORMAT` \| `HDR_FORMAT(802_11=2)` \| `HDR_INFO(hdrlen/2)` \| `WLAN_IDX` \| `OWN_MAC` |
| w2 | `FRAME_TYPE` \| `SUB_TYPE` \| `MULTICAST` \| `FIX_RATE` |
| w3 | `REM_TX_COUNT(15)` \| `BA_DISABLE` |
| w5 | `PID`（`>=3` 时置 `TX_STATUS_HOST`） |
| w6 | `FIXED_BW` \| `TX_RATE` |
| w7 | `SPE_IDX`（双链固定速率取 24） |

### 4.5 MCU 命令（全部 `cid 0xed`，`Q_SET` + `S2D_H2N`，投 qid20）

| 命令 | ext | 载荷 |
|---|---|---|
| RX_HDR_TRANS | 0x47 | 8 B，`hdr_trans=0` |
| MAC_INIT_CTRL | 0x46 | 4 B，`{enable, band}` |
| DEV_INFO_UPDATE | 0x2a | 20 B，hdr + ACTIVE TLV |
| CHANNEL_SWITCH | 0x08 | 76 B；**`rx_path` 是链路数量**（`hweight8`），不是掩码 |
| BSS_INFO_UPDATE | 0x26 | hdr + OMAC(12) + BASIC(24) + RF_CH(8) + BMC_RATE(12) |
| STA_REC_UPDATE | 0x25 | hdr + BASIC + **嵌套 WTBL_RESET_AND_SET**（GENERIC/RX/HDR_TRANS） |
| SET_DRR_CTRL | 0x36 | `MT_STA_BSS_GROUP` |
| EFUSE_BUFFER_MODE | 0x21 | 每 `0x400` 一页，`format=((pages-1)<<5)|(i<<2)|1` |

## 5. 当前状态（3.97）

```
eeprom: chip=7916 band0=2GHz/2 band1=5GHz/3 chainmask=1f flash_mode=1
eeprom-upload: 4 页 ret=0
radio-up: rx-hdr-trans=0  mac-init=0  dev-info=0  channel-switch=0  bss-info=0  sta-rec=0  drr=0
data-init: rx 18024540 base/cnt/cidx=63   tx 18024420   txfree(18024520) base=0 → 需主机武装
tx-probe: desc buf0=TXD(32) buf1=frame(34) ctrl=00204022 → 80204022 (DMA_DONE)
          didx 0→1；**无 TXS、无 TX-free、无 TX-done**
data-recv: didx=0（从未收到任何帧）
```

## 6. 卡点

> 引擎取走描述符并置 `DMA_DONE`，固件不产生任何完成事件。

`DMA_DONE` 是 WFDMA 引擎写回描述符的位，只证明它读完了 buffer——不是"帧发出去了"。
真正的判据只有 TXS / TX-free / TX-done，而这三个从未出现过。

剩余嫌疑集中在两层，都在 WF 空间（`0x820e4000+`，band1 为 `0x820f4000`），
走 BAR 窗口访问，不是现在 `crw` 直接打 CR 的路径：

1. **MAC 初始化层**。原厂 `NICInitializeAdapter` = `WfMacInit` → `WfPhyInit` →（空壳）。
   `WfMacInit` 依次 `chip_wait_hif_dma_idle` / `AsicInitMac` / `AsicAutoFallbackInit` /
   `AsicSetMacMaxLen` / `asic_init_wtbl` / `AsicRxHeaderTransCtl` /
   `AsicRxHeaderTaranBLCtl`×3 / `AsicAutoBATrigger`。对应 mt76 的
   `mt7915_mac_init_band`（`MT_TMAC_CTCR0`、`MT_MDP_BNRCFR0/1`、`MT_DMA_DCR0`、
   RMAC/WTBLOFF airtime 与 backoff）。**native 线完全没有这一层。**
2. **AP 启动收尾**。原厂 `APStartUpByBss` 在 `wdev_do_open` 之后还有
   `UpdateBeaconHandler` → `AsicSetPreTbtt` → `chip_interrupt_enable`。
   native 线做到 BSS/STA_REC/DRR 就停了。

## 7. 已排除的假设（别再重试）

| 假设 | 结论 |
|---|---|
| efuse 能读出 MAC / 校准 | 否。`MCU_EXT_QUERY(EFUSE_ACCESS)` 有应答但载荷恒空，8 B / 24 B / 两种 s2d 全试过 |
| RX 环武装值决定投递 | 不全是。`64` 投递一次、`0` 不投、`depth-1=63` 也不投；当时环号本身就错 |
| 数据帧可以单段 DMA | 否。TMAC 从 `buf1` 取 802.11 头，单段时 `buf1=0` ⇒ 静默丢弃 |
| `0x18024520` 是数据环 | 否。那是 MCU_WA_MAIN（TX-free 事件环）；数据环是 `0x18024540` |
| `dma_done` 等于"帧走了" | 否。只是引擎读完 buffer |
| `fw-state=7` 等于固件健康 | 否。那是主机写的 TOP_MISC 镜像；WA 核卡死时它仍是 7 |
| `BSS_INFO_BASIC.bmc_wcid` 会建 WTBL 表项 | 否。要单独发 `STA_REC_UPDATE` + 嵌套 `WTBL_RESET_AND_SET` |
| `3.92` 那个 TX-free 是"第一帧的完成" | 否。是 qid2 被误当数据环武装的产物 |

## 8. 后续路线（按依赖顺序）

1. **WF 空间读回能力**（只读，不必刷机）：把 `MT_TMAC_CTCR0`、`MT_MDP_BNRCFR0/1`、
   `MT_DMA_DCR0` 的现场值读出来——已配好则嫌疑转向第 2 条，全 0 则确认是第 2 条。
2. 照 `mt7915_mac_init_band` 补齐 band 级寄存器。
3. beacon + TBTT + 中断使能（`APStartUpByBss` 的收尾）。
4. 验证 TXS 语义（`pid>=3` + `TX_STATUS_HOST` 已设，但从未有 TXS）。
5. RXD 解析（`RXD0[31:27]` 包类型 + `[15:0]` 长度），拿到第一个真包后校正偏移。
6. WTBL 速率表（RA）——固定速率是否绕过这一层尚未验证。
7. wiphy / mac80211 接入（netdev、`cfg80211_ops`、TXQ/AC 映射、sta 生命周期）。
8. band1 / 5G。
9. PPE/NPU 硬件加速绑定——项目最终目标，也是唯一没有先例可参照的一段。

## 9. 复现

设备侧探针全部走 `/proc/zx-csp-wlan/{ctl,status}`，`commit=1` 才真正落寄存器。

```
l1profile | dma-init | wfsys-reset | fw-state | fw-dl wm|wa | fw-start | fw-plan
eeprom-init | eeprom-upload
rx-init <0|1> | mcu-recv <0|1> | mcu-ext <id> [hex] | mcu-cmd
radio-mac <band> | radio-chan <band> <ch> | radio-bss <band> | radio-up <band> <ch>
radio-sta <band> | data-init | data-recv | txfree-init | txfree-recv
tx-bcast | tx-probe [dump] | mac-set <12hex>
crw <addr> <val> | win <bar> <off> [n] | rings | mcuwin
```

一键脚本在 `out/fw-boot397.sh`（Windows 侧，SSH 驱动）。逆向工具在 `native/tools/re/`。

## 10. 代价与约束（实测）

- **一个 boot 只有一轮"复位 → 下载 → RDY"**：同一次开机里重复 `wfsys-reset`，
  ROM 不再回到下载态。
- **命令写错会把 WA 核打死**：事件环停在最后一条成功应答上、命令环 `didx` 不再前进，
  唯一恢复手段是重新刷机。
- **`status[]` 只有 16 KiB 且满了静默丢写**：事件的 hex dump 会把结果行挤掉，
  所以默认关 hex（`evt_log=0`）。
- 刷机脚本**不能管道给 `head`**：SIGPIPE 会打断升级流程。
- 单次开机只能验证一个信道（第二次 `CHANNEL_SWITCH` 不应答）。

## 11. 一句话总结

前四个阶段的"原厂行为对齐"是成立的（下载、校准、band0 配置、描述符布局都有实机证据）；
**从"引擎读走描述符"到"帧出现在空中"之间还差两层主机侧初始化**，这两层目前是空白，
也是这条线下一步唯一要做的事。
