# 驱动对齐与逆向移植报告（v1.5 轮，2026-10-28）

> 目标：逆向原厂各项驱动并移植 OP，无线/有线硬件加速正常工作，WiFi 信号与
> 速率对齐原厂（2.4G 协商 ≥500M），交付驱动来源 / 移植范围 / 验证结果三件事。
> 约束不变：固件只做静态验证（构建 + verify_pkg/verify_img + squashfs 解包），
> 不刷机；所有结论区分 [实测] / [推断]。

## 0. 一句话结论

- **有线**：原厂 PPE 硬件加速在我们的 6.18 驱动里已工作（≥395 Mbit/s 实测过），
  本轮修掉它打破 IPv6 TCP 的 trap bug，默认开启 —— 与原厂行为对齐（原厂 IPv6
  走自己的 IPv6 分类器，我们暂时走 CPU，正确性对齐、加速差一档，见 §3）。
- **WiFi 速率/信号**：找到"2.4G 协商上不了 500M"的直接原因并修复 —— provisioning
  从未设置 htmode，netifd 回落 HT20（~287M PHY 上限）；原厂 DBDC 是 2x2 HE40
  （574M PHY）。已改 HE40+noscan，5G 补 HE80。RF 校准数据本来就是原厂的
  （wifi 分区 caldata 全量透传）。
- **WiFi 硬件加速**：完成移植范围评估，**决策 = 不随固件发货**（§4）：原厂加速
  hook 在其私有 WiFi 栈内部（CSP_WLAN，无 cfg80211），与 mac80211/mt76 无法对接；
  可行路径是移植 cnjn SR1010 树的 zx279133 IDM/NP 全家（14 文件 ~145KB，GPL，
  远端可得），工程量人周级且必须真机迭代——发货未测试的 DMA 驱动代码只会变砖。

## 1. 原厂驱动的权威事实（来源与出处）

- 原厂内核 = Linux 4.1.25 / Buildroot 2015.08.1，配置 `/proc/config.gz` 全量
  留档：`refs-pr25469/e2631_vendor_config.txt`。
- 模块清单 + 校验和：`build/board/kopull.out.txt`（telnet 拉取，md5 记录）；
  运行时加载表：`board/pass12.out.txt` / `stock-firmware.out.txt`（/proc/modules）。
- 本板真机 DTB：`refs/e2631_live.dtb`（见 refs-local《外围驱动矩阵》S5）。
- WiFi 栈实物：`/etc/wireless/mt7916/`（`board/etc-wireless.out.txt`）：MTK 私有
  固件 `WIFI_RAM_CODE_MT7916.bin`(1.76MB)、WACPU RAM、EEPROM(4KB)、DBDC profile
  `mt7916.dbdc.b0/b1.dat`(7.3KB×2)、l1profile——**dat 文件仅被列出、未被拉取**。

关键符号（[实测] 自原厂配置）：`CONFIG_CSP_WLAN=y`、`# CONFIG_CFG80211 is not
set`、`# CONFIG_WLAN is not set`、`CONFIG_ZX_TM=y`、`CONFIG_IDM_HW_MIRROR=y`、
`CONFIG_IDM_SKB_RECYCLE=y`、`CONFIG_WIFI_SKB_RECYCLE=y`、`CONFIG_ZX_NET_ZERO_COPY=y`、
`CONFIG_ZX279128S_ASIC=y`。含义：**原厂 WiFi 驱动完全游离于标准 Linux 无线栈之外**
（自有 netdev + dat 配置，无 cfg80211/mac80211），加速经 tm/idm 直挂其私有驱动。

## 3. WiFi 速率 / 信号对齐：本轮改动与剩余差距

**已修复 [推断，待真机复测]**
- provisioning（`e2631-wifi-ap`）与自带 `/etc/config/wireless` 从"无 htmode/
  HE20"改为：2.4G = **HE40 + noscan**（对齐原厂 DBDC 2x2 HE40=574M PHY，
  noscan 对齐其强制 40M 行为），5G = **HE80**。此前 2.4G 在 HT20 下 PHY 上限
  ~287M——这就是"协商速率无法达到 500M"的直接原因。
- RF 校准数据**本来就是原厂的**：wifi 分区（JFFS2）里 0x30000 字节 caldata
  （芯片 ID 0x7916）经 `11-mt76-caldata` 全量透传给驱动（含 precal/DPD 区，
  与原厂驱动 memcpy 的用法一致）[实测-代码链路]。
- 5G 23dBm（CN）此前已真机验证（20→23dBm，2026-10-24）[实测]；2.4G 20dBm
  为 CN 法规上限，双方同限。

**剩余差距（诚实清单）**
- 原厂 `mt7916.dbdc.*.dat` 的逐速率 SKU/IGI/波束调优（7.3KB×2）mt76 不消费；
  该文件当时**未被拉取**。要进一步对齐覆盖，需从原厂机拉取这两个 dat 做逐项
  对照（只读操作，符合 §0.1），把可映射的项（如 min_txpower/basic rate/
  chainmask）落到 hostapd/uci。
- 真机 A/B（同点位信号强度 RSSI、协商速率、吞吐）待用户放行刷机后进行。

## 4. 无线硬件加速：移植范围评估与决策

- 数据通路事实 [实测-源码]：PPE 分类器只看交换口入向（`zx279128s-ppe.c:313-324`
  是防呆，非瓶颈），WiFi 入向走 PCIe→CPU，**不经交换织物**；原厂 WiFi 加速 =
  tm/idm 私有 DMA 直通（`/proc/modules`：`tm 2 mt7916,switch`——hook 在私有
  驱动内部）[实测-运行时]。
- 可行路径 = 移植 zx279133 的 IDM/NP/TM 驱动族到 ZX279128S + 6.18：需新写
  ① DMA 描述符与 NAPI 收包（对照 6.18 API）、② skb 归属与 IDM_SKB_RECYCLE
  语义、③ 流表老化与 FDB 同步、④ **mt76 侧的入向挂钩**（原厂挂钩点在私有
  驱动里，mt76 侧没有等价物——需要扩展 mac80211→IDM 的递交路径，属新设计）、
  ⑤ 与 PPE/trap 的共存（本队 IPv6 trap 修复的下一层）。参照源码远端可得
  （cnjn SR1010，GPL），本地无副本。
- 工程量：人周级（4-8 周）+ **必须真机迭代**（DMA 驱动离线验证无法证明安全）。
- **决策：本轮不随固件发货**。发货未经真机验证的 DMA 引擎驱动 = 变砖风险；
  WiFi 流量继续走 CPU 软转发（~200M 架构上限，非 bug）。此结论与清单 P2-7
  第一步分类一致，差异清单已具备，后续开工有完整路线。
