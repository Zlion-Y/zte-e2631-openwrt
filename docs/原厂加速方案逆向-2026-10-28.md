# 原厂有线+无线硬件加速方案逆向报告（2026-10-28）

> 目标：完整还原原厂（E2631，cspkernel 4.1.25）有线与无线加速的详细方案，
> 供决策"我方方案是否全部替换"。全部结论标注证据来源；[实测]=二进制/运行
> 时证据，[推断]=由符号与结构推断。

## 0. 总架构（一句话）

**原厂的有线和无线加速是同一套东西**：ZTE 自家 Linux 4.1 fork（"cspkernel4.1"）
内建的 **FFE（Fast Forward Engine）+ NPU 卸载** 子系统，外加以模块形式加载的
**tm.ko（引擎编程层：分类器/哈希匹配 RAM/QoS 调度器）**；有线驱动 switch.ko 与
无线驱动 mt7916.ko 分别通过 `ffe_learn_skb/ffe_receive_skb`（有线）与
`idm_skb_stack_push/pop + Kernel_ASEND`（无线）两对接口挂入同一条快速路径。
控制面在 `/proc/zte/sys/ffe/cmd`。

```
                    cspkernel4.1（内建，不加载）
  ┌────────────────────────────────────────────────────────┐
  │  FFE: ffe_main/ffe_flow/ffe_flush/ffe_sk_buff/         │
  │       ffe_fk_buff/npu_main/ffe_sharedata/ffe_proc      │
  │  QC(CSPKernel_*：队列控制)  dev_mirror(IDM_HW_MIRROR)   │
  │  wan_bridge/br_component  nf_conntrack_pt(联动flush)    │
  └───────▲──────────────────────────▲─────────────────────┘
          │ ffe_learn_skb/           │ idm_skb_stack_push/pop
          │ ffe_receive_skb          │ Kernel_ASEND
  ┌───────┴────────┐        ┌────────┴─────────┐
  │  switch.ko     │        │ mt7916.ko(MTK栈) │
  │ (SBRG+ONU注册) │        │ (5.6MB,7760函数) │
  └───────┬────────┘        └────────┬─────────┘
          │ spa_set_hashram/matchram │ aclWLANToIDMEssid* (tm.ko)
  ┌───────▼──────────────────────────▼─────────┐
  │ tm.ko（引擎编程）：cla_*(77) spa_*(70)      │
  │ adm_*(36,QoS桶/信用/警务) tm_*(329) pon_(65)│
  └───────┬────────────────────────────────────┘
          │ 寄存器
  ═══════╪══════ 硬件：PPE 分类器/修改器(0x9200_0000)、
          │       SBRG 交换、TM 调度(0x9234_0000)、
          │       NPP(0x921c_0000)、IDM(0x921c_8000)
```

## 2. 有线加速：原厂详细方案

1. **驱动注册**：switch.ko（SBRG 交换 + ONU 公共功能注册 `sw_public_{onu_mactable,qos,statistics,port_cfg,ratelimit,vlan}_func_reg`）把网口交给 FFE（ingress/egress notifier 模型）。
2. **首包学习**：新连接首包走内核栈；`ffe_learn_skb` 提取 `ffe_flow_key`（五元组+入口 dev），学习成功后把流交给 NPU（`ffe_npu_filter_flow` 过滤哪些协议可卸载，`ffe_npu_get_flowmaxid` 是流表容量上限）。
3. **NPU 直转**：后续包由 NPU（PPE 分类器/修改器，即我方 ppe.c 驱动的那组 0x92000000 表——hash/match RAM 由 `spa_set_hashram/matchram` 编程）直接转发，不进栈。
4. **例外回收**：NPU 不认识的帧由 `ffe_receive_skb/fkb` 送回栈（`backlog_rx`）。
5. **状态联动**：conntrack 删除/变化时 `ffe_flush_flow_by_conntrack` 精确刷流；组播变更走 maddr4/maddr6 flush。
6. **QoS/整形**：tm.ko 的 ADM（桶/信用/警务/颜色）在快速路径上保 QoS；`CSPKernel_skb_SelectQueue` 保选队一致。
7. **发送加速**：`Kernel_ASEND`（"ASEND Tmsgcn"——Tx 消息链）为驱动提供绕栈直发。

**与我方方案对照**：同一组硬件分类器，控制面不同——我方 = mainline `nf_flow_table` offload（fw4 flowtable → `TC_SETUP_FT` → ppe.c 建流），只有 IPv4 TCP/UDP，384 条哈希，IPv6 被架构性拒绝（本轮 trap 修复保证 IPv6 走 CPU 的正确性）；原厂 = 自研 FFE 控制面，**协议覆盖面更大（含 IPv6 分类器、L2、组播 flush）**，且 QoS(ADM)/选队与快转一体。

## 3. 无线加速：原厂详细方案

1. **挂入**：mt7916.ko（MTK 私有栈，5.6MB/7760 函数）不 import 任何 tm 数据面 API——它的数据面直连内核快速路径：
   - **TX**：`Kernel_ASEND`（加速直发）；
   - **RX/交接**：`idm_skb_stack_push/pop`——IDM 的 skb 栈（无锁交接结构），WiFi 帧从 MAC DMA 出来后压栈，FFE/NPU 侧弹出并按流处理；
2. **分类维度**：tm.ko 的 `aclWLANToIDMEssid*` 按 **ESSID** 建 ACL/映射（多 SSID 场景每 BSS 独立入快速路径）；`dev_mirror`（IDM_HW_MIRROR）提供镜像通道；
3. **无 per-flow 表反复写**：与有线共用 NPU 流表（`ffe_npu_*` 同一套）；
4. **这正是我方做不到的**：mt76 的收发不走 `idm_skb_stack`/`Kernel_ASEND`——这两个入口是 cspkernel 内建符号，mainline 内核根本没有；mac80211 的队列模型与 FFE 的 fkb 直交接不兼容。**所以"给 mt76 挂原厂加速"= 把 FFE+IDM+NPU 全套移植到 6.18 + 写一个 mt76 侧的新交接层**（原厂等价物藏在私有驱动里，需逆向其调用量化行为）。

## 4. 替换决策建议（三选项）

- **A. 保持现方案，补短板（推荐）**：留 mainline flowtable，扩展我方 ppe.c——①IPv6 流卸载（原厂分类器硬件本身支持 IPv6，zwzzrl 已证 NPU caps `npu_ipv6_l3tcp*`；需要造 IPv6 键表+保留 IPv6-trap 语义）；②L2/组播 flush 联动；③控制面默认开、IPv6 修复保真。工作量：人级（1-2 周），风险低，硬件同源。
- **B. 全替换为 FFE 移植**：把 FFE+IDM+tm.ko 编程层整体移植到 6.18。**先做一件事：向中兴索取 GPL 源码**——泄露路径写着 `/zte/csp/opensource/`，内核 GPL 下厂商有义务提供 cspkernel4.1 对应源码（含 protocol/ffe/ 全部 8 个文件 + tm/switch 模块源码）；拿到源码工程量才有意义（否则纯反汇编 1.27MB tm.ko 不现实）。预计仍需数周+真机迭代。
- **C. 混合**：有线保持现方案（已达标），无线加速单独立项（B 的子集）。

我方建议：**先发 GPL 索取函/工单拿 cspkernel4.1 源码**（成本最低、收益最大——拿到即全盘皆知），期间按 A 补 IPv6 流卸载；B 仅在拿到源码后再评估。
