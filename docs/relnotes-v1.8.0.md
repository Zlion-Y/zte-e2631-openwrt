## 这个版本做了什么

在 v1.7 的基础上，修掉六个由**第一台真实用户设备**暴露出来的问题。它们全部是"能刷能跑、但某处
不对"的缺陷，不是新功能：

1. **WAN 侧网页访问（新增 80/443）**
   盒子挂在主路由下时，SSH 可用但浏览器打不开后台——WAN 区只有 22 放行。现在 22/80/443 对
   `192.168.0.0/16` 与 `10.0.0.0/8` 开放，`http://<wan-ip>` 直接进 LuCI。
   **首启无 root 密码，刷完请立刻设密码**（同网段任何人都能进）。

2. **在线升级不再诱导降级**
   `e2631-upgrade check` 原来按字符串比较版本（tag `v1.3` vs 本地 `OpenWrt v1.7`，永不相等），
   于是把 v1.3 报成"有更新"。现在按数字逐段比较（`1.10 > 1.9`），并且**非更新版本默认拒刷**
   （需要时用 `E2631_UPGRADE_FORCE=1`）。运行版本读不到时不做判断。

3. **47 MiB userdata 分区此前永远无法初始化**
   窗口起点 `0x3f00000` 被手抄成 `66384896`（正确 `66060288`），初始化脚本每次都拒绝执行。
   现在用 `$((0x3f00000))` 计算，实测可格式化 376 个擦除块 → 42.6 MiB 卷 → 挂载 37.5 MiB，
   写入测试通过。

4. **UBIFS 超级块判断的字节序写反（5 处）**
   盘上是小端 `31 18 10 06`，脚本比较的是大端 `06 10 18 31` 的 md5 → 永远判"未格式化"，
   extroot 永远不启用。`e2631-preflight` 还顺带修成读 UBI 卷（原来读裸 mtd 的 `UBI#` 头）
   并用正确的 sha256。

5. **`USE_PROCD=0` 让两个开机服务空转**
   `rc.common` 判断的是 `[ -n "$USE_PROCD" ]`——字符串 `0` 非空，脚本被当成 procd 托管，
   `start()` 被替换成空壳。受影响的是 **extroot 激活门**（永远不会启用挂载）与
   **netmod 调优**（RPS/XPS/IRQ 亲和从未在开机时执行）。

6. **版本号改为三位**
   从本版起 `/etc/e2631-version` 与发布 tag 统一为 `vMAJOR.MINOR.PATCH`。

## 实测状态（2026-10-29，真机）

| 项 | 结果 |
|---|---|
| 有线 | 端口 1000M full、rx/tx/CRC 错误 0；PPE 接管（`ppe_active=1`，54 条流，skip/fail 0） |
| 无线 | 2.4G **HE40**（ch1，40 MHz）、5G **HE80**（ch36），双频自动广播；RF 校准用原厂 caldata |
| IPv6 | wan6 拨号正常，`ping6` 外网通 |
| 升级路径 | 双槽 serial 78/80，运行槽 = 槽1（OpenWrt），槽0 原厂完好 |
| WAN 侧访问 | `ssh root@<wan-ip>` 与 `http://<wan-ip>` 均可用 |
| 47 MiB 分区 | 格式化+挂载+读写通过；默认仍**关闭**（启用会切走 /overlay，配置不自动迁移） |

已知限制（与上版相同或本轮确认）：
- 首启 AP 约 **69 秒**才广播（有线 ~10 秒就能进后台，早进会看到无线"已禁用"，属时序）；
- Wi-Fi 关联硬死机与冷启偶发挂死仍未根治，有 pending 自恢复兜底；
- 硬件流卸载会打断 IPv6 TCP（本版驱动已让 IPv6 trap 恒开、走软件路径；IPv6 不进 PPE）；
- 有线吞吐无法在本轮硬件上测出上限：PC 的 USB 网卡在坞内 USB2.0 总线上（~300M），
  而本地终结 TCP 的端点都是 1 GHz A9——记录见 `docs/有线吞吐测量-2026-10-29.md`。
